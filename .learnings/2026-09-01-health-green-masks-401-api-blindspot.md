## 一、08:30 版结论错在哪

我在 08:30 写下的判断是：

> 「`backtest_reports` 46 天零落库的**真因**是宿主机调用未带 `X-API-Key`，
> 导致 201 次 401」

**这个因果判断是错的。** 深挖后实锤：

### 实锤证据：401 全部落在巡检中枢自己的运行窗口内

把 201 次 401 按"间隔 >60s"归批，得 **17 批**（每批 14 个不同接口）。
把每批时刻（UTC→北京 +8）与 `automation_runs` 表比对：

```
08-31 09:14  ✅落在 09:13~09:16（本自动化 automation-1785982929477）
08-31 10:23  ✅落在 10:23~10:26
08-31 11:26  ✅落在 11:26~11:28
...（14 批全部命中，14/14）
```

**反向验证更致命**——巡检中枢近 101 次运行中：

| 时段 | 运行次数 | 是否有 401 |
|---|---|---|
| 08-27 21:22 ~ 08-31 07:58 | 87 次 | **全部 ★无 401** |
| 08-31 09:13 ~ 09-01 06:57 | 14 次中有 401 的 | 14 次 |
| 08-31 15:52 / 18:31 / 19:52 / 22:18 / 09-01 00:45 | 5 次 | **★无 401** |

两个决定性事实：

1. **08-31 09:13 之前，87 次运行一次 401 都没有** —— 401 是有起点的，不是长期存在的生产故障
2. **同一自动化在 15:52、18:31、19:52、22:18、00:45 这几轮也没有 401** —— 说明不是脚本固定逻辑，而是**该轮 agent 做没做 API 探活**

起点 08-31 09:13 = 第 31 轮，正是我开始执行"回读验证 / 工程深挖"的轮次。

**真因**：是**我（历轮巡检 agent）在回读验证时自拼 `curl` 探活 QTS API，没带 `X-API-Key`**。
所以它与 `backtest_reports` 零落库**没有因果关系**——那两个问题只是同时存在。

## 二、★ 真正的教训（升级候选）

### 1. 观测者效应：监控系统会污染被监控对象

巡检 agent 每轮手动 `curl` 探活 → 在服务端日志里留下 401 → 我新加的检查项
把这批 401 读出来 → 报成"生产调用链漏配 key → 数据不落库"。

**整条链路里，"污染源"和"告警者"是同一个进程。**

> ★ **新增一个检查项之后，第一次告警出来时，第一件事是问：
> 这个信号有没有可能是我自己（或我的同类定时任务）造成的？**
> 判据：① 异常是否有明确的**起始时间点**（长期存在的才可能是真故障）
> ② 把异常时刻与 `automation_runs` 里**所有**自动化的运行窗口做包含比对
> ③ 找"运行了但没产生该异常"的**反例轮次**——有反例 = 不是脚本固定行为

### 2. 时间相关 ≠ 因果

401（24h 内）与 `backtest_reports` 零落库（46 天）在时间上重叠，我就把它们串成了因果。
但两者量级都对不上：401 从 08-31 才开始，表从 07-16 就停了 —— **46 天的停滞不可能由 1 天前的现象造成**。

> ★ **把两个现象写成因果前，先对齐时间量级**。这是零成本的证伪检查，我却跳过了。
> 一句"401 只有 1 天历史，表停了 46 天"就能当场否掉这个归因。

### 3. 归因要能解释"为什么之前没发生"

08-31 已经修了 SQLAlchemy `text()`（16 处，CI 绿），但表还是零落库。
我急着给"修复后仍无效"找一个解释，于是 401 成了最顺手的答案 —— **先看结论后找证据**。

> ★ **"修复后没效果"时，正确反应是回到链路从头梳理，不是就近抓一个异常当解释。**
> 特别是在刚加完新检查项、手上正拿着一个"新鲜的异常"的时候，误配概率最高。

### 4. （保留）`/health` 全绿确实会掩盖业务接口错误

这一条本身没错：`/health` 2826 次全绿，同时 201 次 401，信噪比 14:1。
**检查项 `check_qts_api_auth()` 保留** —— 它抓的是真实维度，只是这次抓到的是自伤信号。
修好探活后它会转为正常守门（401 归零，有真实漏配时能抓到）。

# 🔄 2026-09-01 11:20 二次修正（真因终局，接 run#53）

> 上文第二节「真因：我（agent）自拼 curl 探活」**仍然不对**。
> 「401 落在巡检中枢自己的运行窗口内」这个观察是对的（确实自污染），
> 但**层判错了**：不是 agent 手工动作，是**脚本固定行为**。

## 真正的机制

`check_code_quality()` 里 `pytest tests/ -q` 用了**相对路径且未锁 cwd**。
本自动化的调度 cwd 是 **QTS 仓**，于是「Claw 工程质量检查」实际在跑 **QTS 的 tests/**：

```
tests/test_e2e.py                     → /api/v1/stocks/index/realtime、/api/v1/signals/、
                                        /api/v1/backtest/results、/api/v1/stocks/realtime/600519、
                                        /api/v1/stocks/pool、/api/v1/account/summary ...
tests/contracts/test_strategy_api.py  → /api/v1/stocks/realtime/600519.SH、
                                        /api/v1/stocks/realtime/999999.XZ、POST /api/v1/backtest/run
```

全部对 `http://localhost:8000` 直连且**不带 `X-API-Key`** → 每次巡检固定 **14 条 401**。

## 决定性对照实验

| 运行方式 | cwd | pytest 实际跑的 | 401 |
|---|---|---|---|
| `import module; main()` | Claw | Claw 485 项 | **0** |
| `python unified_ops_center.py` | QTS 仓 | QTS tests/ | **14** |

唯一差异 = cwd。修复（锁 `cwd=CLAW_ROOT` + 绝对路径）后，以 QTS 为 cwd 重跑 → **新增 401 = 0**。

## 为什么「agent 自拼 curl」这个解释能骗过我

它满足了我当时掌握的全部证据（窗口吻合、有反例轮次、起点在 09:13），
而**脚本固定行为**同样满足这些证据，且能更好地解释「每批恰好 14 条、接口顺序完全一致」
这种机械规整性 —— 人工探活不可能这么整齐。**能对上证据 ≠ 唯一解释。**
