**等级**：P1（**假绿灯**：唯一守护「记忆尾部不可见」的检查，6 天来一直在查一份没人读的副本；
真正被注入的那份已顶到可见边界、且带着 4 项从未被发现的缺陷）
**类型**：blind-spot（检查对象错位 · split-brain · false-green）
**状态**：已修复（检查器纳入被注入副本 + 声明回写 + 证据库重编号），2026-10-14；A/B 合并待用户决定

## 1. 现象

每日记忆维护的 PHASE1（1a 文件大小 / 1a-2 可见余量）与两个检查脚本
（`~/.workbuddy/scripts/check_memory_visibility.py`、`Claw/.workbuddy/scripts/memory_headroom_check.py`）
**一直只查** `~/.workbuddy/MEMORY.md`（下文记 **A**）。

A 侧 10-09 ~ 10-13 的结论：**「连续 6 日零增长 / 可见余量 599B 🟢 / 六判据 rc=0」**。

而平台**实际注入**给模型的是 `~/.workbuddy/user-24688a34-…-personal/MEMORY.md`（下文记 **B**）。

| | A（一直在查） | B（**实际被注入**） |
|---|---|---|
| 路径 | `~/.workbuddy/MEMORY.md` | `~/.workbuddy/user-24688a34-…-personal/MEMORY.md` |
| 字节 / 行 | 96,609B / 468 行 | **99,461B** / 484 行 |
| 规则 / 证据 | 72 / 72 | **76 / 75**（不匹配） |
| 规则层止 | 6,754B（余量 **+599B**） | **7,915B（余量 −2B）** |
| mtime | **10-11 03:36**（冻结） | **10-13 08:04**（活跃） |
| 检查覆盖 | 每日 6 判据 | **0 条**（检查表里没有这个路径） |

B 侧一次都没跑过的四项机器判定：
① 规则层结束偏移 7,915B ≥ 上限 7,913B（**第 76 条铁律压在可见边界**）
② 规则 76 条 / 证据 75 块不匹配
③ 索引头「75 条各一行」「止于 **6,994B**」两处**声明腐烂**
④ 证据库「用法」行仍指向旧副本 A

## 2. 决定性取证：怎么知道「被消费的是 B」

1. **消费侧比对（最强）**：当日注入块的 `# 关 — 长期记忆` 正文与 B **逐字一致**，且其规则**首条**是
   A 里**根本不存在**的 `automation_update` 关思考模式（A 首条是「搜到 ≠ 验完」）。
   系统提示里 Layer 2 声明的路径也正是 B。
2. **mtime 体检**：A 的 mtime 停在 **10-11 03:36** —— 那正是**上一次维护自动化写它**的时刻；
   B 的 mtime 是 **10-13 08:04**（后续会话仍在写）→ 冻结的那个是副本，活跃的那个才是被消费的。
3. **播种链**：B 于 **10-07 18:36** 由 A 播种（当时同为 96,849B，personal/ 下 SOUL/USER/IDENTITY 同批复制）；
   **10-09 08:21** 留 `.bak`；此后 **A 被 10-10 16:13 的会话压缩**（96,849→96,577，`.bak-20261010T161205`）
   而 **B 未跟**（B 继续长到 99,461B / 76 规则）→ 由此**文本分叉**：同一条规则 A 是压缩版、B 是长文版。

## 3. 为什么危险

检查器的**输入路径**是从历史文档 / 提示词里抄来的，而**被消费的对象**由平台决定 —— 两者分家后：

> 「文件存在、可读、内容自洽、检查通过」**四件事全部成立**，却与「模型实际读到什么」无关。

这是「上游失败 → 下游静默产出旧结论」的**更隐蔽变体**：这里**连"上游失败"都没有** ——
没有任何一步出错，只是**问错了对象**。危害指向本技能的第一性原则：**尾部不可见才是故障**，
而唯一在守护它的那个检查，守护的是别人的尾巴。

## 4. 顺带挖出：B 的证据编号**整体偏移 +1**（比缺 1 块更严重）

规则首条（`automation_update` 关思考模式）是在**库首插入**的，证据库未同步重编号。

实测口径：取每个证据块的第一个 `- ` 行与规则行做**归一化前缀比对**（去空白/标点/反引号）：

| 关系 | 命中数 |
|---|---|
| 证据 N == 规则 N | **0** |
| 证据 N == 规则 N+1 | **75 / 75** |

⇒ 按文档契约 `grep -n "── 证据 N ──"` 取到的是**规则 N+1 的证据**，**且不报错**。

**通用教训**：判据「条数相等」只能抓「缺条目」，抓不到「错位」——
一旦有人把条数补齐（本次修复前它就是 76 vs 75），**错位就再也测不出来**。
**修「数量型」缺陷时必须同时补一条「顺序/对齐」断言。**

## 6. 判据（写进技能，可复用到任何"检查某文件"的场景）

> 先找**消费侧**（谁注入 / 谁读取 / 谁解析这个文件），路径**从那里取**，不从历史文档取；
> 再留一条**消费侧自证**断言：「本检查的目标 == 本次实际被消费的那份」。
> **没有这条断言，「检查通过」只证明"副本没问题"。**

反例形态（本次原文）：`wc -c` 正常、`rc=0`、结论「零增长 🟢」、余量「599B 充足」——
而真正被注入的那份，余量是 **−2B**。
