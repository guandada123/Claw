# ★升级候选 —— 「降级可见」≠「降级被计量」：61/300 只代码静默回退 T-1 旧K线，评估仍报"正常"

**日期**：2026-10-15（Alpha101 因子评估自动化 automation-1786666500469）
**等级**：P1（**结论可信度**——20% 面板缺当日 K 线，而报告/退出码/达标数全部显示正常；本次 kept 结论未被翻转，但机制可复现）
**类型**：silent-degradation / 计量缺口（降级有 WARNING 但未进入健康判据）
**状态**：本次未改代码；缓存已由复测自然重写（现 293/300 终点为 10-15）。规则缺口待固化。

## 1. 现象

`alpha_eval.py --sample 300` 本次输出**完全正常**：

```
股票池 300 只 | 因子 24 个 | horizon=1
达标因子(3): ['alpha5', 'alpha11', 'alpha15']
报告: .../alpha_eval_20261015.json     退出码 0，无 🔴
```

同一次运行另有 **62 条 stderr WARNING**（被 `tail` 截断前共约 57 行可见，同一代码重复出现 3-4 次）：

```
[alpha_data] WARNING 002034: PG 刷新失败，降级使用 48h 前的旧缓存
```

即：**61 只股票的 bars 用的是 10-14（T-1）的 K 线，10-15 当日线缺失**，而评估照样出报告、
照样出 kept 清单，**没有任何一处把"降级比例"写进结论**。

## 2. 取证

| 检查项 | 结果 |
|---|---|
| `bars_*.csv` mtime 分布（运行后） | 237 个 = 今天 17h（刷新成功）；**62 个 = 10-14 17h（未刷新）**；1 个 = 今天 10h |
| 62 个未刷新的 CSV 最后交易日 | **61 个 = 2026-10-14**；1 个 = 2024-07-02（已退市/无新数据，属正常） |
| PG 直查（复刻 `load_bars` 的 SQL，COUNT） | **12/12 全部命中（n=360~671）** → **不是数据缺失** |
| `cache_bars()` 复测（62 只全部重跑） | **62/62 成功刷新** → 失败是**瞬时**的，非持久性故障 |
| 报告新鲜度（反证非陈旧缓存） | `n_days` 669 → **670**；与 10-14 报告逐因子对比 **24/24 全变** |
| 4 分钟后 PG 健康 | ✅ 正常（上述探针） |

→ 结论：运行窗口内发生**若干次瞬时 PG 读失败**（与 `qts_client._query` 注释里已记载的
"colima 端口转发偶发抖动"同源），但**失败被 per-code 吞掉，未汇入任何总量判据**。

## 3. 根因

```
alpha_data.load_bars(code)                     ← 与 qts_client._query 的加固口径不一致
  try: with qts_client._pg() as conn: ...
  except Exception: return None                ← 裸捕获、无 RETRY、无 rollback、不丢连接
      ↓
cache_bars: PG 失败 → 有旧 CSV 就打 WARNING 降级返回
      ↓
alpha_eval: 逐 code 调用，只看"有没有 df"，不统计降级数
      ↓
报告只有 n_stocks/horizon/kept，无 degraded 字段 → 评估层无法自证输入质量
```

关键对比：同一仓的 `qts_client._query()` 在 2026-09-04 已加固为
**「异常时 rollback + close 再丢弃，每次重试强制新建连接」**（防 `InFailedSqlTransaction` 卡死在同一污染连接上），
但 `load_bars()` 走的是 `_read_sql(连接)` 直连路径，**绕过了这套加固**，且复用的是模块级
全局连接 `_conn`（`with conn` 在 psycopg2 里只是事务包装，**不关连接**）。

## 4. 教训（待周度升级为铁律）

1. 🔴 **"可见降级"必须同时"被计量"。** 打 WARNING 只解决了"不静默用旧值"，
   没解决"结论里看不出用了多少旧值"。凡有降级分支的批量循环，必须返回
   **降级计数**并被主流程纳入判据（例：`degraded_ratio` 超过阈值 → 报告标 `partial`、退出码非 0）。
   与既有铁律「**框架级『成功』≠ 真实产出**」同源：这一次"成功"是真的成功，只是**成色只有 80%**。
2. 🔴 **同一份数据的两条取数路径，加固必须同口径。** `_query()` 有重试/丢连接，
   `load_bars()` 没有 → 后者成为**唯一漏网路径**。加固一处不等于加固一类；
   检查方式是搜"还有谁在直接持有全局连接"。
3. 🔴 **判"运行是否健康"不能用退出码 + 达标数**（这两个都由**被观测的同一层**产出）。
   本次最有效的判据是**盘外可算的 `bars 最后交易日分布`**——293/300 应为当日，
   61 个停在 T-1 一眼可见。这正是「数据完整性检查基准必须来自库外」的实例。
4. ⚠️ **有降级 ≠ 结论必错。** 本次 kept `[alpha5, alpha11, alpha15]` 未变、三个因子 ICIR
   (0.486/0.328/0.336) 距 0.3 保留线尚有余量，故**未重跑**（遵循自动化"异常不重复执行"约束）。
   判断"要不要重跑"的口径应是 **降级比例 × 该结论距阈值的距离**，不是"有没有警告"。

# 【2026-10-16 补充】遗留①结案 + 根因收敛：这是「多线程共享单连接」的自伤，不是外部 PG 抖动

## A. 遗留①（48h vs 24h 疑点）—— 结案：**两次测量不是同一个对象状态**

`age_h` 在 `alpha_data.py:190` 由 `csvf.stat().st_mtime` **在调用当刻**算出，并直接进 WARNING 文案。
而 `BARS_CACHE_TTL_HOURS = 24`，故一个 code **只有在缓存年龄 >24h 时才会进入回源分支**——
推论有二：

1. 该 WARNING 报出的 age **必然 ≥24h**，且**每失败一天就 +24h**（24h → 48h → 72h…）。
   昨日文案报 48h，说明那批文件在**告警当刻**的 mtime 约为 10-13 17:10（=48h），
   **并非** 10-14 17:11。
2. 我昨天"磁盘实测 24h"是**告警之后**、且在**复测把 62 个 CSV 全部重写成功之后**测的 → mtime 已被刷成 10-15。
   两个数字测的是**同一文件的两个不同时点**，不矛盾。

**教训归属**：这不是新坑，是既有铁律「**比对口径须对齐**（算法+粒度+**时点**）」的又一实例——
"告警文案里的量" 与 "事后磁盘态的量" 不可直接相减。**取此类量必须带上时点**。

## B. 根因收敛（新增证据，比昨日更进一层）

昨日结论为"运行窗口内若干次瞬时 PG 读失败"。本次证据把它**收敛为并发自伤**：

| 证据 | 观测 | 指向 |
|---|---|---|
| 同 code 告警重复 | 11 个 code 出现 2–3 次（如 300937/000932/002075/002268 各 3 次） | 同一次 run 内**并发**多次调用 `cache_bars(同一 code)` |
| 调用图 | `alpha_eval.run_ic()` → `ThreadPoolExecutor(max_workers=8)`；每 code 循环 24 因子调 `compute_factor()`，而其内部**又**调 `cache_bars()`（`alpha_factors.py:296/315`），另有 `alpha_eval.py:106/141` | 单 code 在一个 run 内被**多线程/多路径**读同一缓存 |
| 连接口径 | 全部走 `qts_client._pg()` 的**模块级全局连接** `_conn`（`with conn` 仅事务包装，**不关连接**） | psycopg2 连接**非线程安全** → 并发下部分线程必失败 |
| 落盘终态 | 31/33 降级 code 的 CSV `last=2026-10-16`、`mtime=10-16 17:10`（=**今日**） | 兄弟线程**成功**并覆写了文件——**同 code 一边失败一边成功** |
| 盘外探针 | PG 只读探针 **14/14 命中**（`daily_quote` 数据到 10-16，n≈672） | PG **本身健康**，非持久故障 |
| 另 2/33 | 000861 `last=2024-08-05`、600823 `last=2024-05-15` | **已退市**，无当日线属正常，非数据缺失 |

→ **根因**：`load_bars()` 的裸 `except Exception: return None` **叠加**「8 线程共享单一 psycopg2 连接」，
制造出**自伤式**失败；外部（colima 端口转发）抖动最多是放大因素。
→ 这也解释了昨日"瞬时失败"为何**每次只打掉 10–20% 而非全部**：竞态本就是概率性的。
→ 危害等级维持 P1，但**修复优先级上升**：昨日以为要等网络治理，实为**自身并发口径**可闭环。
