## 根因
告警生成逻辑把**「观测到的状态」直接映射为「处置动作」**：
```
isExpired == true  →  "需扫码重登"      # 隐含假设：停摆由过期导致
```
这个隐含假设从未被验证。而真实因果是：**通道先因故停摆（抓取 07-20 停止），登录态后来才自然过期（08-23）**——过期是停摆的**结果**而非**原因**。因果倒置导致 13 次误导。

这类缺陷的隐蔽性在于：所有可观测指标（`isExpired`、`article_count`、`容器 running`）都"正常报错"，单看症状完全正确，**只有跨源比对时间戳（最后抓取 vs 过期时点）才能证伪**。

## 连带发现（同类，一并固化）

### A. 注释里的「实证数字」会腐烂
docstring 写「抓取比过期早停 23 天」，实算 33 天——**注释写了就算数，没人复核**。
→ **规则**：注释里凡是带具体数值/日期的"实证"结论，视为**会腐烂的数据**。改动相邻逻辑时必须重算并同步更正，否则后人（含 AI）会拿错误数字当输入继续推理。本次即为反例：若信了 23 天，会倒推出"抓取 07-31 停摆"的错误时间线。

### B. 未记账运行 + 未提交改动 = 丢失风险
18:06 的实质性修复**既没写 automation memory，也没 commit**，工作区挂了近 1 小时。若期间触发双副本审计（每日 21:00）或 `git checkout`，改动会静默丢失。
→ **规则**：巡检类自动化若**改动了脚本本身**，必须在同一次运行内完成 `commit` + memory 记录，不可留待下次。

### C. 我的初判被实证推翻（再次印证取证铁律）
回读发现 16:53 → 19:11 间隔 137min，初判"17:53/18:53 连漏两档"。取证后确认：**中间 18:07 有一次未记账运行**，实际间隔为 73.5min / 64min，属正常档位。
→ **不取证就下结论 = 制造假告警**。凡"间隔异常"类判断，先查是否有未记账运行，再看是否真漏档。
