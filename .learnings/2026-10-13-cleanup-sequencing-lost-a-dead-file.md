# ★升级候选 —— 复合语句里的「复制→校验→删源」有覆盖竞态：我弄丢了一个死文件

**日期**：2026-10-13（双目录残档专项·死 cost 库归档）
**等级**：P2（**协议执行失误**——丢的是全仓零引用的死文件【12KB 旧版成本库】，功能影响为零；但失误机制可复现到**有引用文件**上，届时就是 P0）
**类型**：destructive-op sequencing / verify-vacuous（三步压缩进一条命令 + 自比对空校验）
**状态**：文件不可恢复（恢复路径穷尽，见下）；机制教训固化于本文。

---

## 1. 现象

归档 `cost.db` / `cost_tracker.db`（两处目录各一份、同名）时，一条复合语句
同时做了「复制→校验→删源」，结果：**12KB 的 .workbuddy 侧副本被 0 字节的
data 侧副本覆盖后删除**，归档里只剩 0 字节版本。

## 2. 失误链（逐步复现）

```
rm  归档里的重复副本（本可作备份）      # 第 1 步：自断后路
cp  data/侧的0字节本 → 归档路径         # 第 2 步：覆盖掉已入归档的12KB副本
md5(归档本, data侧本)                    # 第 3 步：此时两者已同一文件 → 自比对恒相等
rm -f data侧本  .workbuddy侧本          # 第 4 步：删两个原位 → 12KB内容湮灭
```

**两个独立缺陷叠加**：
1. **三步未分离**：复制/校验/删源同一复合语句，且 `cp` 顺序错误（后一个 `cp` 覆盖了前一个已归档的成果）；
2. **空校验**：md5 比对的是「刚被覆盖的文件」与「覆盖来源」——**自己与自己比**，恒真，等于没校验。

## 4. 教训（待周度升级为铁律）

1. 🔴 **「先复制→校验→再删源」三步必须三条独立命令**（或独立工具调用）执行，
   每步之间可停下检查——压缩进一条复合语句 = 把中间态暴露给覆盖竞态；
   已有铁律文字正确，但**执行形态**错了（本条是执行层补充）。
2. 🔴 **同名双源归档：先并排复制（带来源后缀）、比对两个来源、确认**保留哪个**，
   再删源**——绝不在删除前用其中一个覆盖另一个。
3. 🔴 **校验的对象必须是「已归档副本 vs 待删源」，且两者此刻须是不同文件**
   （inode 或 md5 均需先确认非同一实体）；任何"自比对"都是空校验。
4. ⚠️ 影响分级：本次受害者为死文件（零引用）故影响为零；**同一失误若发生在有引用
   文件上即为 P0**——按「机制风险按最坏影响分级」原则，此教训按 P0 级流程修正执行。
