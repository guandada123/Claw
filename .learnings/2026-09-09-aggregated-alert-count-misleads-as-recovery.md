# 聚合型 alert 的「条目数」被误读成「问题数」，制造虚假康复信号

日期：2026-09-09（统一巡检中枢 run#118 发现）
级别：P1（观测性缺陷，已污染历史记录）
★ 升级候选

## 现象

统一巡检中枢 stdout 打印：

```
⚠️ 自动化健康: 1 项异常
```

而同一轮 `unified_self_heal_log.json` 里那条 alert 的正文是：

```
自动化健康 10 项🔴: 投顾操盘周报(336h)；周综合复盘(173h)；股票池体检(336h)；……
```

前一轮 run#117 据 stdout 写下记忆：**「自动化健康 10🔴→1 项，调度饿死存量基本清退」**。
实际当轮日志正文是 **9 项🔴** —— 不是清退，只是少了 1 个。虚假康复被写进了长期记忆。

## 根因

`unified_ops_center.py:2922`

```python
print(f"  {status} {name}: {len(res['alerts'])} 项异常")
```

打印的是 **alerts 列表长度**。而多个检查把 N 个子问题**聚合进一条字符串**返回：

```python
return {"ok": False, "alerts": [f"自动化健康 {n_crit} 项🔴: {detail}"]}
```

于是 `len(alerts)` 恒为 1，与内含的真实问题数（10）差一个量级。
alert 正文只进 `all_alerts` + self_heal_log，**从不打印到 stdout** ——
巡检日志里唯一可见的数字，恰好是那个会误导的数字。

## 修法

在 alert 循环里补一行正文出口（截断 220 字符）：

```python
print(f"       alert: {a if len(a) <= 220 else a[:220] + '…'}")
```

只打印，不改判据、不改推送行为、不进 all_alerts 二次计数。
与 run#63「note 只进字典从不输出」是同一先例、同一修法。

验证：ruff 0 / 501 passed / `--dry-run` 确认 `1 项异常` 后紧跟 `自动化健康 10 项🔴`。

## 可迁移铁律

1. **「条目数」≠「问题数」。** 聚合型返回值（一条字符串装 N 个子问题）会让计数与实际严重度
   差一个量级。任何 `len(list)` 式的健康度打印，必须确认 list 的粒度就是问题粒度。
2. **数量骤降优先怀疑口径，而非康复。** 10→1 这种断崖式好转，若无对应的修复动作/代码变更，
   先回读原始正文核对，再写"已解决"。**虚假康复比虚假告警更贵**——它会终止调查并写进记忆，
   后续轮次沿用，错误自我复制（run#117 已实际发生）。
3. **告警正文必须有 stdout 出口。** 只进日志文件的正文等于没有：巡检日志是人唯一会看的界面，
   界面上缺正文，就只能拿计数当结论。这是 run#63 同类缺陷的第二次复发，说明
   "数据进了字典但没有输出通道" 是本文件的结构性易犯点，新增检查时须自查出口。
4. 与既有纪律呼应：run#54「dedup/主打印的合并回显不可当归因依据，必须回读 self_heal_log
   原始 reason」—— 本次证明该纪律不仅适用于归因，**同样适用于计数与趋势判断**。
