# ★ 凭据轮换必须枚举「全部持有者」，且按文件清单而非目录猜测（2026-10-12）

## 现象
2026-10-11 轮换 Wind token 时，我宣布"换了三处"（`.env` 两个键 + `~/.workbuddy/mcp.json` 五个 server），
并据此判定轮换完成、把 PA-013 结案。**实际遗漏两个活跃消费方**：
1. `~/.wind-aifinmarket/config` —— **Wind CLI 的全局配置，在其凭据解析顺序里优先级最高**（存在即返回）；
2. `~/.workbuddy/connectors/.../tokens/wind_analytics_key.txt` —— connector 的 token 文件。

后果：`.env` 里明明已是有效新 key，**CLI 永远读不到**（先命中全局配置里的旧值）→
CLI 持续返回 `认证失败：无效的apikey`（HTTP 401）→ 主数据源（鱼盆表）继续空产。
次日早上该任务的自动化自己挖出并修复（两处同步 + 权限 0600 + 回读哈希比对）。

## 根因（两条，都是我自己的方法错误）
1. **我只看了"命中列表的前 10 行"就动手**：当时扫描输出是「仍持旧 token 的位置: 755（只打印前 10）」，
   前 10 全是 mcp.json / 其备份 —— 真正要更新的那两个被排在后面，没进我的视野。
   → **凭据类排查必须按"去重后的文件清单"逐个确认，不能只看前 N 条。**
2. **扫描根目录是"我猜的"**：我只扫了 `~/WorkBuddy`、`~/.workbuddy`、`~/Library/LaunchAgents`，
   而 `~/.wind-aifinmarket`（第三方 CLI 的全局配置目录）根本不在根里 → 必然漏。
   → 消费方可能在**你没想到的目录**：应按「全 home + 文件名/关键词反查」或读 CLI 的配置优先级文档来枚举。

## 正确做法（可复用）
- 轮换后 **双向全盘复核**：①旧值残留（期望 0，且要区分"活跃配置" vs "历史日志/备份"）；
  ②新值分布（逐个确认是活跃消费方）。两者都要**按文件去重列表**输出，不能只给计数或前 N 条。
- 对"同一事实多副本 + 有优先级"的链路（`.env` / 全局配置 / connector token）：
  **必须逐个消费方验证功能可用**（本例正解 = 跑一次 CLI 拿真实返回值，而不是看 .env 写对了没有）。
- 结案前问一句：**"还有谁在读这个值？"** —— 能被 grep 到的不止你想到的那几个目录。

## 影响与处置
- 19 个交易日的主数据源空产**不是本次造成的**（此前已在空产，真因一直被误判为"Wind 积分耗尽"）；
  我的漏改让**修复晚了约 17 小时**（10-11 16:38 → 10-12 09:06 自动化自行发现并修）。
- 现已全盘复核：旧值仅存于**会话日志/备份**（38 文件，非活跃配置）；新值分布在 4 个活跃文件（7 个键位）。
