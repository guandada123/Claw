# docker logs 按流分流：只读 stdout 会让日志检测静默失效

- **日期**: 2026-08-30
- **项目**: Claw（统一巡检中枢 `unified_ops_center.py`）
- **级别**: ✅已升级(2026-08-30)（跨项目通用工程陷阱，静默失效无报错）

## 现象

巡检中枢 `check_wechat_channel()` 有一路检测：扫容器日志统计 `ret=200013`（微信风控）次数，
命中即报"风控态，禁止重登空转"（F7 分支）。该分支**从建成起从未触发过**，
日志里长期显示 `200013: 近6h=0/全窗口=0`，被误读为"确实没有风控"。

## 根因

`docker logs` 把**容器的 stdout 投到调用进程的 stdout、stderr 投到 stderr**（按流分流，不合并）。
而该容器的业务日志（Python logging 默认走 stderr）**全部在 stderr**：

| 流 | 行数 | 含 `[Fetch]` |
|---|---|---|
| stdout（uvicorn access log） | 25807 | **0** |
| stderr（业务日志） | 2101 | **358** |

检测代码用的是 `run_cmd(...)` → `subprocess.run(capture_output=True)`，
然后 `for line in r.stdout.splitlines()` —— **只读了 stdout**，业务日志一行都扫不到。

后果是**静默失效**：不报错、不异常，只是永远返回 0，看起来像"检测通过"。

## 修复

```python
r = run_cmd(["docker", "logs", "--timestamps", container, "--tail", "5000"])
for line in (r.stdout + "\n" + (r.stderr or "")).splitlines():   # 必须合并两流
    ...
```

## 教训 / 通用规则

1. **凡"扫日志"的检测，必须合并 stdout+stderr**，或显式用
   `subprocess.run(..., stderr=subprocess.STDOUT)` 合并。只扫 `.stdout` 是默认错误。
2. **"检测值为 0"不等于"没有该现象"**——先验证检测本身能否看到正样本。
   本次验证手段：在 stderr 里找一个只可能出现在业务侧的标记（如 `[Fetch]`），
   确认合并后能被扫到，才算证明检测链路通。
3. 静默失效类 bug 的特征：无异常、无告警、输出恒为"正常值"。
   对这类检测要**主动造正样本验证**，不能靠"长期没报过"来默认它健康。
4. `docker logs --tail N` 只回溯近期（本例 `--tail 5000` 仅到 2 天前），
   查历史事件需改用 `--since <duration|RFC3339>`（如 `--since 1200h`）。

## 附带教训：症状级告警会给出错误的处置建议

同一路检查的 F3 分支报"登录过期，需扫码重登"，连续 13 轮推送无人处置。
取证后发现处置建议是**错的**：

- 容器最后一次抓取：`2026-07-20 14:19 UTC`
- 登录过期时点：`2026-08-22 23:54 UTC`
- → **抓取比登录过期早停 33 天**，登录态根本不是停摆根因，扫码重登无法恢复。

规则：**给 remediation 之前先做时序对齐**——把"故障开始时点"和"告警症状出现时点"对比，
若症状晚于故障发生，则该症状不是根因，据此给的处置步骤必然无效。

已据此在代码中新增 F3 细化分支：抓取远早于过期即停摆时，
改报"重登大概率无法恢复，建议摘除该巡检项或确认上游调用方"。
