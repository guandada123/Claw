# 2026-10-12 · 归档必须校验条目数 —— 否则"归档成功"是假的 ★升级候选

## 事故形态（差点造成不可逆数据丢失）
MarvisBridge 下线清理时，流程是「先归档 → 再删（入废纸篓）」。
第一版归档命令：
```bash
tar czf "$A/marvis-bridge-final-20261012.tgz" -C /Volumes/ZHITAI --exclude='.git' workbuddy_marvis_bridge
```
**静默产出 144B / 1 个条目**（只打了目录本身，内容一个没进去）。
当时的下一步是 `trash` 整个目录 —— 如果**先删后验**，结果就是：
**归档是空的 + 原件在废纸篓**（还可恢复，但若废纸篓被清就彻底没了）。

## 根因
`tar -C <dir> <name>` 这种"切到父目录再打子目录名"的写法在本次环境下没有按预期展开内容
（`du -sh` 同目录也返回过 0B，同一环境异常，未深究）。
**关键不是这个 bug，而是：归档是"删除前的唯一保险"，它的成功必须是可验证的，而不是"命令没报错"。**

## 判据（可机器校验，本次已在用）
归档后**必做两项校验**，缺一不可：
1. **文件数对账**：`tar tzf X.tgz | grep -v '/$' | wc -l` ≈ `find <dir> -type f -not -path './.git/*' | wc -l`
   （允许 ≥ 实际：软链/隐藏项会使归档侧略多；但**绝不能少于实际** ✗）
2. **关键子目录 grep**：对"最怕丢"的目录逐个确认能 grep 到
   （本次：`grep -c 'claw/done'` = 58、`grep -c 'results'` = 69 ✅）
另外把 `ls -lh` 的体积也看一眼 —— **144B 的"归档"** 是自明的异常信号。

## 正确做法（已改用）
```bash
cd <被归档目录> && tar czf <归档> --exclude=.git .     # 先 cd 再打内容
```
本次结果：**12M / 522 条目**，含全部工作区数据 ✅

## 铁律候选
**「删前归档 = 归档 + 校验 + 才允许删」三件套**：
凡"先备份/归档再删除"的流程，备份与归档**必须带可核对的判据**（条目数、关键路径存在性、体积量级），
判据不过 → **中止删除**。仅凭"命令退出码 0"就当归档成功，等于把唯一保险押在一个未验证的假设上。
（同族：本仓既有铁律「日志成功 ≠ 数据落库，凡写库须 readback」。）
