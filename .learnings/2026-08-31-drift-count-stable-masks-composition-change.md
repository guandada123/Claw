# 漂移「计数持平」会掩盖「组成变化」，且修复动作自身的改动最易漏入库

- **日期**: 2026-08-31
- **项目**: Claw（统一巡检中枢 `unified_ops_center.py` 回读环节）
- **级别**: ★升级候选（巡检/回读类通用陷阱，会导致修复做了一半就以为完事）

## 现象

巡检中枢每轮回读都记一句「`.workbuddy/scripts/` 未提交 4 项，与上一轮持平，无新增」。
连续 12 轮（run#22–run#33）都是「4 项持平」，于是每轮都判定「无新增、不处置」。

本轮（run#34）偶然逐文件名列出，才发现**组成早就变了**：

| 轮次 | 4 项的实际组成 |
|---|---|
| run#22–#31 | db_backup_rotate / mainboard_scan_pool.json / wind_deep_report / **refresh_close_20260824.py(??)** |
| run#32 之后 | db_backup_rotate / mainboard_scan_pool.json / wind_deep_report / **scan_expanded_pool.py(M)** |

一个旧项出列、一个新项入列，**计数恰好都是 4，于是「持平」掩盖了「新增了一个改动」**。

## 更严重的一层：修复自身的改动漏入库

顺着这一线索追下去，发现两处**已完成、已验证、但从未入库**的修复：

1. **`.gitignore`** —— run#32 本人修的（把 `_refresh_close_*.py` 放宽为 `*refresh_close_*.py`），
   修完只更新了 memory，**没有提交**。此后 3 轮回读都盯着「scripts 目录」，
   而 `.gitignore` 在仓库根目录，**不在观察范围内**，于是从未被发现。
2. **`.workbuddy/scripts/scan_expanded_pool.py`** —— 08-31 09:36 的 psycopg2 优雅降级修复，
   闲置 3 小时未入库，被「4 项持平」的惯性结论归入「他人 WIP」而漏掉。

两者都在 **tracked 文件**里（`git checkout -- .` / `git reset --hard` 会直接抹掉），
属于 run#21 已定义的高风险类别，却因为计数没变而一直没被处理。

## 根因

1. **回读只比对计数，不比对集合** —— 「持平」被当成了「无变化」的同义词。
   集合的差集（新增 / 消失）才是信号，计数只是集合大小。
2. **观察范围有洞** —— 回读固定看 `.workbuddy/scripts/`，
   而修复动作可能改到仓库根（`.gitignore`）、`tests/`、其它目录。
   **自己动手修的东西，恰好落在自己不看的目录里。**

## 通用检查清单（★）

1. **回读漂移必须比对「集合」而非「计数」**：列文件名做差集（新增/消失），
   计数相同也要逐项看。写 memory 时**把文件名列出来**，不要只写「N 项持平」。
2. **修复动作收尾时，自检「改动落在哪个目录」**，并**显式把该目录纳入下一轮回读范围**。
   尤其是仓库根配置文件（.gitignore / pyproject / ruff.toml / CI workflow）。
3. 对 tracked 文件里的**已完成 + 已验证**改动，按 run#21 规则 pathspec 精确提交；
   「总数持平」不构成不提交的理由。
4. 功效验证必须**复现故障条件**（本轮：模拟 psycopg2 缺失，旧版抛 ImportError / 新版返回空 dict），
   只跑正常路径等于没验证 —— 与 run#30 的「修法成立与否必须复现故障条件」同源。
