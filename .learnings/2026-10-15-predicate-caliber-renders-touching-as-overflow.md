# 判据的「口径」也会说谎：把「恰好贴边（余量 0B）」报成「已经溢出 2B」

**日期**：2026-10-15（记忆维护日跑，daily）
**等级**：P1（**假失败**：检查器连续两轮报告一个不存在的事实，会诱导「去修不存在的溢出」或「学会忽略这条红」）
**类型**：forensics-caliber（判据的度量口径与它所回答的问题不同口径 · false-positive）
**状态**：已修复（口径修正 + 证伪实验），2026-10-15；规则层余量 0B 的**结构性处置**待用户决定

---

## 1. 现象

用户级记忆（**B** = `~/.workbuddy/user-24688a34-…-personal/MEMORY.md`，实际被注入的那份）
连续两轮（10-14 / 10-15）被 `check_memory_visibility.py` 判红，原文：

```
规则层结束偏移 7915B ≥ 上限 7913B → 有规则落在可见区外（溢出 2B）
```

10-15 逐字节复核结论：**一条规则都没出去**。

## 2. 取证：字节级三查（可复用）

```
1) 末条规则行的独占结束偏移 = len('\n'.join(lines[:rule_last]).encode()) = 7,913
   ⇒ 该行最后 1 字节落在 offset 7,912 —— 正好是「上限 7,913B」内的最后一字节 ✅
2) offset 7,913 / 7,914 是什么？→ "\n\n"
   ⇒ 是「末条规则 → 下一个 `## ` 标题」之间的**分隔空行**
3) offset 7,915 起是什么？→ "## 项目"
```

⇒ 被算作「溢出」的那 2 字节是**分隔空行**，不是任何规则内容。

## 3. 根因

```python
rule_off = len('\n'.join(lines[:rule_end]).encode()) + 1
```

取的是「**规则层段落**结束偏移」——把「末条规则 → 下一节标题」之间的分隔空行算进了规则层，
还额外 `+1`；而判据③ 回答的问题却是「**末条规则可不可见**」。

**问题与度量不同口径** ⇒ 当规则层恰好填满可见区（余量 = 0B）时，
「刚好贴边」被渲染成「已经溢出 2B」。

## 4. 为什么这比「漏报」更值得写下来

它的方向与已知同族事故（「取不到证渲染成通过」）**相反**，但同属「输出不描述事实」。
假失败会诱导两种错误处置：

1. 有人去修一个**不存在**的溢出（浪费一轮，且可能顺手改坏别处）；
2. 读者学会**忽略这条红**（狼来了）—— 下次**真**溢出时不再被当真。

⇒ 对「日常红」的容忍度，是被**假红**一点点喂出来的。

## 5. 判据

> **判据的"分子"必须与它要回答的那个问题同口径。**
> 问「全部规则可见吗」→ 取**末条规则行的独占结束偏移**，判 `> limit`；
> 问「余量够不够大」→ 那是**另一件事**（本工作流交 1a-2，阈值 500B）。
> **不要用一个判据同时答两件事** —— 否则两件事会互相污染对方的结论：
> 「够不够大」被回答成「有没有出去」，于是 0B 被读成负值。

## 6. 落地（可复现）

先备份 `~/.workbuddy/scripts/_bak-20261015-033524/`（两个检查器 + B 三份，`cmp` 逐字节一致）。

1. `check_memory_visibility._layout`：`rule_off` 改为末条规则行的独占结束偏移；
   旧口径值保留为 `rule_section_end`（仅供诊断）；新增 `headroom = limit - rule_off`。
2. 判据③ 由 `off >= limit` 改为 `off > limit`，文案改为「规则层末条规则止于 NB > 上限」。
3. 输出行增列「可见余量 NB」；`memory_headroom_check` 经 `info['rule_off']` **自动跟随**（无第二处口径）。
4. `--fix` 回写三份文件的「止于 NB」声明（**等长替换 → 三份字节零变化**：96,609 / 69,560 / 100,428），复跑幂等。
5. **证伪实验（必做，否则就是削钝检测）**：
   - 合成「末条规则 +30B」→ 仍报 `溢出 30B` ✅（检测未失效）；
   - 真文件 B → 不再含「可见区外」，余量如实显示 **0B**，🔴 由 1a-2 报出 ✅。

## 7. 顺带结论：0B 是真问题，但没有「非语义」解法

B 的规则层**恰好填满**可见区（余量 0B）。实测：**保留全部语义子句**的压缩上限只有 ≈110B（≈1 天余量），
不构成修复。能真正腾位的只有两条，且**都需用户点头**：

1. 合并 3 条**逐字重复**的 `source|管道` 规则（第 6 / 20 / 30 条，合计 227B → 1 条 ≈105B）
   ⇒ 76→74 条，净释放 ≈120B；须同步合并证据块并**重编号**（10-14 曾因重编号出过整体 +1 的错位，需带对齐断言）；
2. 退役**冻结的旧副本 A**（`~/.workbuddy/MEMORY.md`，mtime 停在 10-11、已不被任何注入消费）
   ⇒ 不解决 B 的余量，但消除「同一事实两处自由」的分叉隐患（正是 10-14 事故的根因）。

**不采用**：「删规则腾地方」（会真的让规则不可见）与「放宽内置上限」（＝把假绿灯再装回去）。
