# ★升级候选：去重标记「先写后发」= 告警静默丢失 + 假成功

**日期**：2026-10-11（全项目审计，P0-2 配套）
**等级**：P1（告警链路可靠性；失败会被 6 小时冷却吞掉，且调用方拿到 rc=0）
**类型**：silent-failure / false-success
**状态**：已修复（去重标记改为**发送成功后**落盘，+3 例防回归测试）

---

## 1. 现象

`push_card.py`（被 20+ 脚本共享的飞书推送中台）的 `--dedupe-key` 逻辑：

```python
# 修复前（错误）
if os.path.exists(df):
    print("已发"); return 0
open(df, "w").write("sent")     # ← 先写标记
ok = send_card(...)             # ← 再发送
return 0 if ok else 1
```

## 2. 危害链（三步静默）

1. 首次发送失败（网络抖动 / 限流耗尽 3 次重试）→ 返回 1，**但标记已落盘**；
2. 6 小时内任何重试 → 命中「已发」→ 直接 `return 0`；
3. 调用方看到 rc=0 → 认为「已告警」→ **告警静默消失且系统自认成功**。

叠加效应：我刚建的持仓新鲜度守卫会把「去重命中」当作成功 → 真实告警永久丢失。

## 3. 修法与边界

- 标记写入移到 `ok=True` 之后（发送成功才落盘）。
- 代价：极端并发下可能重复发送一次（两个进程同时越过检查）。
  **取「偶发重复」而不是「静默丢失」** —— 告警场景里前者可容忍，后者不可接受。
- 3 例测试钉住：失败不留标记 / 成功才留 / 命中短路且不再调用发送。

## 4. 推广判据

- 凡是「**先记账、后干活**」的模式（去重标记、幂等键、已读位点、锁文件）都要问：
  **「如果干活失败，账记错了会怎样？」** 记账必须在**确认成功后**。
- 同族：`日志成功≠数据落库`（写库须 readback）、`退出码只编码需人看`、
  `框架级「成功」≠ 真实产出`。
