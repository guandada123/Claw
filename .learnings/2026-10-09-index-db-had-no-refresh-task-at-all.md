# ★升级候选：已有铁律「静态快照须有刷新脚本+过期告警+备份」未落地到 memory_index.db —— 该库静默停更 111 天

**日期**：2026-10-09（编制《本机记忆系统说明文档》时发现）
**等级**：P1（本机语义检索通道长期返回陈旧数据，无任何告警）
**类型**：knowledge_gap（铁律已存在，但未覆盖到该数据源）
**状态**：已修复 + 已补自动化；规则候选

## 1. 现象

`~/.workbuddy/memory/memory_index.db` 是 `search_memory.py` 的**唯一数据源**。实测：

```
MAX(updated_at) = 2026-06-20 19:00:28      ← 距今 111 天
COUNT(*)        = 1,101 行 / max(id) = 2,846   ← 历史行已被清理
失效文件残留     = 116 个（源 md 早已被蒸馏/删除，索引行还挂着）
分层分布         = ❄️COLD(普通) 1,081 / 🔥HOT 10 / 🌡️WARM 7 / 其余 3
```

后果：任何走 `search_memory.py` 的检索，命中的都是 **2026-06 的记忆快照** —— 与当前 MEMORY.md（10-08 更新）严重脱节，却**没有任何告警**，输出看起来完全正常。
`build_memory_index.py` 的 docstring 还声称「SQLite FTS5 全文索引」，而 `init_db` 里 FTS5 **被显式注释掉了**（理由：unicode61 不支持中文分词），实际走 `LIKE` —— 声明与实际不符，进一步掩盖了问题。

## 2. 根因（三层，缺一不可）

1. **没有刷新任务**。全机 91 条 ACTIVE 自动化中，**没有任何一条**跑 `build_memory_index.py`。脚本存在 ≠ 脚本被调度。
2. **用户从未感知**。它是"读起来像查询"的组件，只有在检索结果明显错误时才会暴露；而陈旧的索引**不报错、不降级、不告警**。
3. **脚本自身有 4 个静默缺陷**，使问题既难发现也无法自愈：
   - `INDEX_DIRS = [Path("/Users/guan/WorkBuddy")]` **硬编码绝对路径** → 换机即静默扫到 0 个文件（且返回"成功"）；
   - **无备份**：全量重建直接覆写，出错无回退；
   - **不清理失效行**：源文件被删/蒸馏后，索引行永久残留（116 个就是证据）；
   - **不清除同文件旧行**：章节改名会在索引里留下永不消失的幽灵段落。

## 4. 防复犯（规则候选）

> **「脚本存在」不是「脚本被调度」。凡引入一个会被下游读取的派生产物（索引/缓存/快照/基线），引入当次就必须同时登记一条刷新任务，并让该任务自身带「过期即告警」的判据。**

三条可执行检查（建议纳入月度审计）：
1. **孤儿脚本扫描**：对 `<scripts>/*.py` 逐个 `grep -r "<脚本名>"` 于 ① 全部 ACTIVE 自动化的 prompt ② 其他脚本 ③ crontab/launchd。**三者皆无引用 = 孤儿**，要么接调度，要么标废弃。
2. **派生产物新鲜度**：对每个 SQLite/JSON 派生产物查 `MAX(updated_at)`（或 mtime），与**库外**基准（交易日历/当前日期）做差集 —— **库内自比答不了"缺什么"**。
3. **声明与实际对照**：脚本 docstring / 文档里写的机制（如"FTS5"）必须与代码实际一致；不一致本身就是缺陷信号。

## 5. 去重

- 与铁律「🔴 静态快照类数据源必须有『刷新脚本+过期告警+备份』三件套」**同一条**，本例是该铁律**未被应用到的第 N 个数据源**。故本条重点不在"新规则"，而在 **「铁律存在 ≠ 铁律被逐资产核对」** —— 建议在月度审计里加一步：**列出全部派生产物，逐个勾选三件套是否齐备**。
- 与铁律「🔴 上游定时任务失败 → 下游静默产出旧结论」同源；本例更进一步：**连上游定时任务都不存在**。
