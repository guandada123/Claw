# ★教训：扫描类检查必须锚定「**实际执行行**」—— 我差点被"修复说明的散文"骗到改坏 3 条自动化

**日期**：2026-10-12（15:00 窗口飞行前检查时）
**等级**：P1（若照第一反应动手，会对**3 条今天要跑的自动化**做无谓改动 —— 白改 + 引入风险）
**类型**：取证口径（正则扫到了散文而非命令）
**状态**：已在动手前自行拦下（导出 prompt 后 grep 才发现已修）

---

## 1. 怎么走到误判的

飞行前检查时，我**亲手**跑了一遍自动化 Step 1 用的表达式：

```bash
bash $CLAW/scripts/is_trading_day.py   →  rc=2
[ "$(...)" = "0" ]  →  "非交易日" → 自动化会 SILENT 退出 ✗
```

**这一步是真的事实**：`scripts/is_trading_day.py` 是 **Python 文件**（单源薄壳），
用 `bash` 解析必然报语法错 → 非 0 ✓。

于是我去扫"哪些自动化受影响"，正则 `bash\s+[^\s|;)]*\.py` 命中 **4 条** → 差点动手改 ✗。

## 2. 真相：命中的是**修复说明**，不是命令

导出那几条 prompt 一看：

```
Bash: [ "$($PYTHON $CLAW/scripts/is_trading_day.py >/dev/null 2>&1; echo $?)" = "0" ] && ...   ← 命令本身已修
（2026-10-12 修：原写 `bash ...is_trading_day.py` —— 它是 Python 文件，bash 解析必然非 0，…）  ← 散文里写了旧写法 ✗
```

**正则命中的正是括号里那句"原写 bash …"** —— 即**记录旧 bug 的说明文字**。

精确复核（只取 `Bash:` / `[ "$` 开头的**执行行**）：
> **真正用 bash 跑 .py 的执行行：0 条** ✓

## 3. 判据（可复用）

> **扫描"配置/命令"类问题时，模式必须锚定到「实际执行行」，不能全文正则。**
> 尤其：**修复说明、示例、反例、变更日志里常常原样引用"旧的错误写法"** ——
> 它们和真正的缺陷长得一模一样。

配套动作（这次救了我的那一步）：
- **改前先导出原文并打印"要改的那几行"** —— 一看就知道命令到底长什么样 ✓
- 扫完**再做一次更窄的复核**（限定行首/代码块），两次口径一致才下结论 ✓

## 4. 同族提醒

- 「在 README / notes 里 grep 到某命令」≠「该命令在配置里」。
- 「grep 到某路径」≠「该路径被使用」—— 本工作区已多次栽在"文本命中 ≠ 语义命中"上。
