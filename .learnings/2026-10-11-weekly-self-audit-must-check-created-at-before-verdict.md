# ★教训：周期性自审的「本周改动」必须**先查 created_at 与派发次数**，再判「有没有用」

**日期**：2026-10-11 晚（首轮「变更效果评估」自动化，周日 20:30）
**类型**：分析口径错误（不是系统故障）
**结果**：避免了一次「机制失效」的假结论；顺手发现 3 个真问题（休市日历缺口 / 排期撞车 / 陈旧注释）

---

## 1. 我差点得出什么错结论

自审任务的 Step 3 预设：「重点核对**本周新机制**是否按设计工作」，并点名 5 个机制
（持仓新鲜度守卫 08:35 / 价格刷新 15:12 / 板块强弱层 15:30 / 处置触发器 15:40 / QTS 备份 02:20）。

如果按字面执行「查它有没有跑、有没有产出」，得到的结论会是：

> ❌「5 个机制全部 0 次派发、无 runtime 记录、产物日期不对 → 机制失效」

**全是假的。** 真相：

```sql
SELECT id,name,created_at,next_run_at FROM automations WHERE deleted_at IS NULL
-- 5 条全部 created_at = 2026-10-11（当天），next_run_at 全在未来（10-12）
```

它们是**当天（周日）刚建**的，`BYDAY=MO,TU,WE,TH,FR` 意味着**首个执行窗口是下周一**。
0 派发不是故障，是**排期还没到**。

## 2. 正确的判据顺序

判「机制是否失效」必须按这个顺序，缺一步就会误判：

1. **created_at** —— 它存在了多久？比 `run start` 更基础。
2. **派发次数**（`logs/automation.log` 的 `run start` 事件计数，**不是** `last_run_at`）
3. **next_run_at 是否在未来** —— 在未来即**健康**，不叫 stale（本轮 80 条活跃自动化 stale = 0）
4. 只有当「创建足够久 + 到过点却没派发」时，才进入「失效」判定。

一句话：**「没跑」有两种，一种是坏了，一种是还没到点。先看 created_at 再下结论。**

## 3. 顺带发现的 3 个真问题（这才是本轮的价值）

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| 1 | 板块层 `report_date` 是**生成日**而非**数据日**；RRULE 只有 `BYDAY=MO-FR`，**不含 A 股休市日历** | `sector_strength.json.report_date=2026-10-11`（周日手动生成），脚本 189 行 `date.today().isoformat()` | 休市工作日会照跑并写入「同源数据但 report_date 不同」的记录 → 给 T2「连续 3 个**不同 report_date**」灌水，把「板块持续弱」提前触发 |
| 2 | 15 点档**排期撞车** | 10-12 15:30 两条同点（板块层 + StockInsight 收盘扫描）、15:40 三条同点（处置触发器 + 一次性核验 + 助理选股扫描）；板块层 15:30 → 处置触发器 15:40 仅 **10 分钟**串行窗口 | 调度器 `concurrency=3` 不实际限流；串行依赖无先后保证校验 |
| 3 | `.gitleaks.toml` 注释与事实不一致 | 注释写「Wind token 轮换**待执行**」（09:02 提交 36bdd08 写下），但 16:38 提交 dc81bc8 已完成轮换；实测旧值 `ak_7w6DGz…` ≠ 当前 `.env` `ak_7qcrs8…` | 陈旧注释会让后续审计**误判轮换未做**，甚至触发无意义的二次轮换 |

## 4. 可复用结论

- **「只读类周期性自审」也要先做事实校准**：时间口径、created_at、派发计数、样本量（本轮 RPS 历史只有 1 个 report_date → T2 结论本就不可能成立）。
- **机制的「首个执行窗口」> 系统的「评估窗口」时，必须显式标注「尚未验证」而不是「无异常」**。本轮 5 个机制全部属于这一类。
- **绿灯不等于证据**：Claw `Security Scan` 在修复前后都是 15/15 全绿，绿灯对「扫描器是否真在扫」零信息量。唯一有效证据是 A/B 对照（rules-less → 0 命中；`useDefault=true` → 2 命中）。
