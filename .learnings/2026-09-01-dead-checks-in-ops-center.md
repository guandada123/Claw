# 2026-09-01 巡检中枢自身审计：15 项检查里 4 项是死检查，note 通道零出口

## 起因
run#46 巡检跑完 15 项全绿 SILENT。按 run#41「静默降级陷阱」教训，对**巡检中枢自身**
做一次"哨兵的哨兵"审计：15 项全绿，是否每项都真的在查？

## 发现（P1）
### A. 4 个检查函数恒返 `ok: True`，无任何变红路径（代码级实锤）
| 检查项 | 函数 | return 分支 | 问题 |
|---|---|---|---|
| 数据新鲜度 | `check_data_freshness` L874 | 2 个 return 全 `"ok": True` | stale 也不告警；且阈值 `mt.date() < today - 1day` 容忍 2 天 |
| 成本监控 | `check_cost_anomaly` L1051 | 3 个 return 全 `"ok": True` | **连 except 分支都返绿** |
| Dependabot | `check_dependabot_backlog` L1076 | 4 个 return 全 `"ok": True` | gh 不可用也返绿；`堆积>10` 只加 flag 到 note |
| 选股去重 | `check_duplicate_picks` L736 | 2 个 return 全 `"ok": True` | 异常分支同样返绿 |

### B. note 零出口 —— 设计意图完全未实现
- 4 个检查的 docstring 都写「仅 note 可见性」，靠 note 提供可观测性。
- 实锤：`grep -rn 'get("note")\|\["note"\]' unified_ops_center.py` → **空**。
- 主循环只读 `res["ok"]` 与 `res["alerts"]`；`_sync_state_anchor` 也不带 note。
- **note 被构造、被 return，然后被永久丢弃。**

### C. `check_schedule_liveness` 自证循环
- 判据：`今日调度锁数 == 0` → 告警「调度系统可能整体挂死」。
- 但中枢自己写 `claw_lock_unified_ops_center_YYYYMMDD`（每日级锁）→ `today_n` 恒 ≥ 1。
- 实测今日锁 = 1 个，**就是中枢自己**。
- **即使其余 62 个自动化全部停摆，该项永不告警。**

### D. 实测掩盖（非故障，但证明检查无效）
4 个数据产物（`qts_daily_signals/regime/signal_consensus/source_weights`）
全部停在 08-31 15:26/15:42（11h 前），09-01 当日 0 更新 → 中枢显示 ✅ 数据新鲜度。
（注：09-01 为交易日，产物本就该在 15:00 后刷新，当前时点 02:55 属正常。
真正的问题是：**若 09-01 收盘后仍未刷新，中枢要等到 09-03 才可能报，且还是假绿不报**。）

## 影响
- 15 项 = **10 项真检查 + 4 项死检查 + 1 项自证循环**。
- 失明维度：数据新鲜度 / API 成本 / 依赖堆积 / 选股冲突 / 全局调度挂死。
- **比漏报更危险的是误导性安全**：用户见「15 项全绿」会以为四维已被覆盖，
  实际这四个维度从未产生过任何一次告警，能力为零。

## 为何不自动修
需设计决策，自动化不得擅自改（run#43 代价不对称原则）：
- 方案 A：给 note 接出口（状态锚 `last_notes` 字段 / 飞书卡新增「观测」段）—— 改动小，恢复可见性
- 方案 B：让 4 个检查真正能变红（需定阈值，如数据产物超 1 个交易日未更新即告警）—— 恢复告警能力
- 方案 C：改名为「观测项」，从 15 项检查中剥离，不再计入 ✅ 计数 —— 恢复诚实性
- 自证循环修法：`check_schedule_liveness` 排除中枢自身锁后再计数。

## ★升级候选
1. **「全绿」不等于「有覆盖」——审计监控系统时，先查每个检查项是否存在变红路径**
   （grep `"ok": False` / `"ok": not alerts`，零命中即死检查）。

2. **「仅 note 可见性」是伪设计，除非 note 有出口**。写这类降级前必须先确认
   消费方存在（`grep 'get("note")'`），否则等于把告警扔进黑洞，比不写更糟
   —— 它制造了"已覆盖"的假象。

3. **自指检查必然自证**：任何"系统是否活着"的检查若把自身计入证据，就永远为真。
   必须排除自身（`今日锁数 - 自身锁`），否则检查恒绿且不可证伪。

4. **恒返 ok 的检查项应从计数中剥离**。把"观测项"混进"检查项"的 ✅ 计数，
   会让覆盖率的分子虚高，是最隐蔽的监控造假。

5. **except 分支返绿 = 把故障变成静默**。巡检类代码的 except 必须返
   `ok: False`（或明确标注 skip 并计数），否则依赖缺失、命令不存在、解析失败
   全部表现为"一切正常"。本次 4 个死检查有 3 个的 except 分支都返绿。

## 取证手法（可复用）
- 静态扫全部 `check_*` 函数的 return 分支，统计 `"ok": True/False/表达式` 数量，
  `okFalse==0 且 okExpr==0` → 死检查候选（再读代码确认，正则仅作筛子不作结论）。
- 死检查的另一面是"note 黑洞"：`grep 'get("note")'` 零命中即无出口。
- 验证自证：跑 `schedule_utils.py stats` 看今日锁是否只有自身。
