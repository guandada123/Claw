# 审计日志被单一高频项灌满：93.5% 是同一条死通道告警

**日期**：2026-09-02（统一巡检中枢 核查）
**等级**：P1（审计留痕失去回溯价值，真实告警被淹没）
**状态**：已修复并验证
**✅已升级(2026-09-06)**：是（「有上限的日志 = 会被高频项独占」属于通用结构性问题）

---

## 1. 现象

`unified_self_heal_log.json` 是 200 条的**环形上限**日志（`data[-200:]`）。
统计 2026-08-26 ~ 09-02 全部 200 条：

| target | 条数 | 占比 |
|---|---|---|
| 微信公众号通道 | **187** | 93.5% |
| QTS API鉴权 | 9 | 4.5% |
| 成本监控 | 2 | 1.0% |
| 自动化健康 | 1 | 0.5% |
| QTS/pmf CI | 1 | 0.5% |

即：7 天审计窗口里 93.5% 是**同一条**「微信登录过期」告警的重复留痕，
真实可处置的告警只剩 13 条，且 08-26 之前的历史已被挤出窗口。

## 2. 关键辨析：**飞书没被轰炸，被灌满的是审计留痕**

排查第一反应是「每小时推送轰炸用户」——**这个假设是错的，务必先证伪**。
取证 `.ops_alerted.json`（告警去重状态）：

| 去重键 | 上次推送距今 |
|---|---|
| 微信公众号通道@wechat-download-api 登录过期 | 61.8h（TTL 72h，未到期） |
| QTS API鉴权@QTS API 鉴权失败 # 次/#h | 20.7h |
| 成本监控@本月累计 ¥#.# / 预算 ¥# | 1.3h |

飞书侧 72h 降频正常生效，用户**没有被轰炸**。
被灌满的只是 `append_heal_log` 的审计流水（脚本注释明确「审计日志照记」）。

> **教训**：看到日志里同一条重复 N 次，先分清是**推送侧**还是**留痕侧**。
> 两者的修复完全不同（前者改去重 TTL，后者改写入节流），归因错了就是白改。

## 3. 根因

```python
data.append(rec)   # 原实现：无条件 append
data = data[-200:] # 环形上限
```

`log_action` 对每次 detect 都无条件追加。死通道项每小时必然命中，
7×24=168 小时就产生 168 条，直接把 200 条窗口吃干。

**放大器**：该项是**外部平台风控导致、无自愈路径**的死通道
（取证：最后真实抓取 2026-07-20T14:19Z，登录 2026-08-22T23:54Z 才过期，
抓取比过期早停 **33 天** → 扫码重登无法恢复）。
既修不好、又停不掉，是完美的噪音发生器。

## 4. 修复

`append_heal_log` 增加**审计节流**（窗口 `AUDIT_THROTTLE_H = 6` 小时）：

- 仅作用于 `action == "detect"`；自愈/修复/失败类动作**一律不节流**（处置留痕不能省）
- 命中同类（`(target, reason[:80])`）且在窗口内 → **不新增条目**，
  只把已存在条目的 `ts` 更新为最近时刻并 `hits += 1`
- 保留「最后一次见到 + 出现过几次」，不丢可见性，也不再挤占窗口

同时压缩存量：200 条 → 9 条（按同类归并，保留 `first_seen` + `hits`），
187 条微信噪音归并为 2 条（旧文案 117 次 + 新文案 70 次）。

## 5. 验证

| 场景 | 期望 | 实测 |
|---|---|---|
| 同类 detect 连写 7 次 | 1 条，`hits=7` | ✅ 1 条 hits=7 |
| 混入不同 target | 另起 1 条 | ✅ 共 2 条 |
| `action=heal` 连写 4 次 | 4 条全留 | ✅ 4 条 |
| 同 target 但超窗(8h) | 落新条目 | ✅ 2 条 |

## 6. 通用教训

**任何「有上限的环形日志」都会被最高频的那一项独占，与该项是否重要无关。**
噪音项的杀伤力不在于吵，而在于**挤掉别人**——
它会让日志在真正出事的那一刻失去回溯价值。

判据：若单一 key 占日志 >50%，先做节流再谈其他，别去调告警阈值。
