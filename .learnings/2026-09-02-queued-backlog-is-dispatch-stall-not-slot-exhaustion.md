# QUEUED 积压 = 派发卡死，不是「并发槽位耗尽」★升级候选

**日期**：2026-09-02（巡检中枢 run#66）
**类型**：归因错误（推断被全样本统计推翻）+ 哨兵盲区

## 现象

09-02 上午，3 条自动化 status 停在 QUEUED 长期不开跑：

| 创建时刻 | 自动化 | 等待时长（至 10:03） |
|---|---|---|
| 09:27:09 | 📋【做T】早盘自检(9:25) | 36min（**早盘窗口彻底错过**）|
| 09:34:04 | 📈投顾·科技红利聚焦扫描 | 29min |
| 09:38:00 | 📊【系统维护】Quant 数据管线 | 25min |

同时 09:43:42.073 一刻中断 3 条已跑 26–53min 的任务（`ACCEPTED` +
`interrupted=true` + `partial_delivered`，产物全丢）。

## 错误推断（必须记住的坑）

先看到 6 条被杀 run 的 `metadata_json` 里 `queuedPosition` **全局连号 1→7**
（跨 session、跨 cwd），且共用同一 `sessionId`，据此断言：

> 「平台自动化全局串行、并发度 = 1，所以后面的只能排队」

**这个结论是错的。** 拉近 7 天 499 条 run 全样本后直接被推翻：

| 指标 | 实测值 | 推翻了什么 |
|---|---|---|
| 真实并发（按 `startedAt`→`finishedAt` 分钟重叠） | p50=1 / p90=3 / **max=10** | 并发**无硬上限**；6 条在跑时照样派发第 7 条 |
| 排队等待 `startedAt - created_at` | p50/p90/**max 全 0.00min** | 正常态**创建即启动，零排队** |
| 等待 >5min 的 run | **0 / 499** | 今晨 25–36min 等待是**前所未有**，非常态波动 |

`queuedPosition` 连号只是队列**编号**，不代表并发上限；`p50=1` 只是平时任务稀疏，
不是串行约束。**用单点字段名去猜系统语义，会得到自洽但完全错误的模型。**

## 真因方向与因果反转

按时间线重建，因果与「中断导致积压」相反：

```
09:11:59  策略执行-09:10   启动 → 至今 IN_PROGRESS (51min)
09:12:09  智能选股         启动 → 至今 IN_PROGRESS (51min)
09:17:24  统一巡检中枢     启动 → 至今 IN_PROGRESS (46min)   ← 派发正常的最后一条
────────── 分界线：此后新建 run 无一启动 ──────────
09:27:09  做T早盘自检      QUEUED，从未 started
09:34:04  科技红利扫描     QUEUED
09:38:00  Quant 数据管线   QUEUED
09:43:42  鱼盆×2 + 盘中监控 被中断（这 3 条是 09:17 之前就在跑的）
```

**卡死（09:17–09:27 之间）先于中断（09:43:42）**。所以不是「中断打坏了调度器」，
而是派发能力先失效，09:43:42 的批量中断更可能是同一根因的另一表现或系统超时清理。

→ 归因纪律④再次验证：**窗口吻合 ≠ 唯一解释**。先按毫秒排时间线定分界点，
再谈因果方向；分界点在哪，根因窗口就在哪，不要拿最显眼的事件（批量中断）当起因。

## 哨兵盲区（已修）

中枢原 17 项**无一**能发现此类故障：
- `check_automation_health()` 只看「**最近一次**运行」，批量中断会被后续成功运行覆盖，
  故 run#57~#65 九轮期间 4 次批量中断（08-31 半径2 / 09-01 半径3 / 09-01 半径2 /
  09-02 半径2）**全部报 ✅**。
- 从未有任何检查读 `QUEUED` 状态 —— 而「到点未执行」对时敏任务（做T早盘自检 9:25）
  比「执行失败」更致命：失败有痕迹会告警，不执行是静默的。

修复：新增第 18 项 `check_automation_queue_backlog()`，改用**瞬时状态量**
（`automation_runs.status` = QUEUED / IN_PROGRESS）+ 同刻聚类求爆炸半径，
不会被后续成功覆盖。阈值：QUEUED ≥3 条或最久 ≥20min；IN_PROGRESS ≥120min
（**排除中枢自身**，其 p90=26min/max=74min，不排除即纯自伤）；中断半径 ≥3 立告，
半径 2 走跨轮 pending 累计 ≥4。

## 锚点幂等坑（同批修复）

聚类 key 用整秒、但锚点 `last_seen_ts` 若也存截断值 → `int(1788313422.073)`
= `1788313422.0` 回写后，下一轮 `1788313422.073 > 1788313422.0` **仍成立**，
同一事件每轮重复告警变「永久红」。**锚点必须存未截断的真实时间戳。**
验证方法：清空锚点连跑三轮 —— 第 1 轮报事件、第 2/3 轮必须「自锚点以来无新增」。

## 可复用规则

1. **拿字段名猜系统语义前，先跑全样本分布验证**。`queuedPosition` 连号 → 并发=1
   是自洽的故事，但 `max=10` 一句话就推翻。单点字段 + 单点观测 = 脑补根因。
2. **「没执行」和「执行失败」是两类故障，需要两套哨兵**。只监控失败率的系统对
   静默漏跑完全失明；时敏任务的漏跑损失不可追回（错过的早盘不会再来）。
3. **状态量优于历史量**。凡「最近一次 X」型指标都会被后续成功覆盖，天然漏报批量
   事件；要发现批量/瞬时故障必须读当前状态快照。
4. **排时间线找分界点，而非围绕最显眼事件解释**。分界点（最后一条正常派发 vs
   第一条卡住）比故障现象本身更能定位根因窗口。
5. **哨兵自身是拥堵源时要显式排除**（本轮中枢自己已跑 46min，就是在跑的 3 条之一）。
