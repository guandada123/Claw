# ★候选铁律 —— 「凭据有效」≠「额度够用」：把耗竭型资源当成常量写进了验收判据

**日期**：2026-10-13（鱼盆数据提取自动化晨间巡检，automation-1783472286775）
**等级**：P1（不造成数据错误，但会让**正确**的修复被误判为回退，进而被回滚或重复排查）
**类型**：verification-scope-blindspot（验收判据漏掉时变前置条件 / 修复与资源是两个维度）
**状态**：无需改代码；待用户充值。本文只修正**归因口径**。

---

## 1. 现象

- **10-12**：修好了 Wind 失效的 apikey（详见 `.learnings/2026-10-12-credential-rotation-missed-cli-config.md`），验收通过 → CLI 返回真实 K 线、主生成器 14/14·20/20、`read_yupen` 转 `today`。结论写的是「已修复」。
- **10-13**：同一个命令、同一份凭据，主生成器又空产（板块 0/14、趋势 5/20）。
- 第一反应极易落到「**修复回退了 / key 又坏了**」——本次巡检的初始假设正是这个。

## 2. 复核（10-13 实测）

| 检查项 | 结果 |
|---|---|
| 三处配置一致性（`.env` / `~/.wind-aifinmarket/config` / connector token） | ✅ 同值，key sha1_8=`4dd6533c`，**未回退** |
| CLI 真实解析链（`cli.mjs call index_data get_index_kline`） | ❌ `backend_error: **账户积分余额不足**`（**不是**「无效的apikey」） |
| 跨数据域（`stock_data get_stock_kline`） | ❌ 同样积分不足 → **账户级**，非工具级 |
| 10-12 产物完整性 | ✅ 14/14·20/20（证明当天修复**确实生效过**） |
| 10-12 日志的时间分布 | 🔴 **11:58** 起已有积分报错 → **修复后仅数小时额度即耗尽** |

→ 结论：**修复没有回退，坏的是另一个维度。** 两个失败面各自独立：

```
失败面 A —— 认证（auth）  ：凭据错/缺失/被轮换漏掉  → 401 / 「无效的apikey」
失败面 B —— 额度（quota） ：账户积分/余额耗尽        → 「账户积分余额不足」
```

10-12 修的是 A；10-13 卡的是 B。**两者错误文案完全不同**，本不该混为一谈，但因为在时间上串起来了，就容易被叙述成「又坏了」。

## 3. 根因（为什么会被误判）

- **验收判据本身是对的**：10-12 用的判据是「跑一次真实 CLI、拿到真实 K 线」，它同时隐含验证了 A 和 B —— 当时额度确实够。
- **错的是把「该判据通过」外推成「此后一直可用」**。额度是**耗竭型资源**，其值是时间的函数；而认证是**状态型资源**，修好就稳定。
- 于是验收结论「已修复」在读者的心智模型里被当成**永久性**事实，掩盖了它其实只在「额度充足」这一**未声明的时变前置条件**下成立。

## 4. 教训（待周度升级为铁律）

1. 🔴 **把「失败面」显式拆开写**：修一个消费方（凭据/额度/网络/权限任一）时，验收结论必须写清修的是**哪一面**，
   以及**没被覆盖的面**是什么。只写「已修复」，读者会自动补全成「全好了」。
2. 🔴 **耗竭型资源的验收必须带余量或带时限**：「跑通一次」对配额类资源只是**瞬时快照**。
   拿不到余量数值时，至少要把结论降级为「**判据通过（在额度充足的前提下）**」并标注复核时限。
3. 🔴 **同一条报错链上「换文案」= 换了根因**：`无效的apikey` → `账户积分余额不足` 是**根因变更的信号**，
   不是同一个 bug 的两种表现。凡看到错误文案变了，先当作新问题独立定位，别沿用旧结论。
   （与既有铁律「数量骤降优先怀疑口径，而非康复」同族：**症状的措辞本身是证据**。）
4. 🔴 **修复类日志里，前一次修复的结论要能被人拿来做减法**：本次如果 10-12 的日志写成
   「认证已通（额度未核）」而不是「已修复」，10-13 的排查可以直接从「查额度」起步，省掉一整轮「是不是回退了」的取证。
