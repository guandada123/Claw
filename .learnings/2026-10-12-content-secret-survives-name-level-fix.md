## 一、事故

准备给 `~/.workbuddy/skills` 加 GitHub 远端时，按铁律先做**推送前凭据扫描**，结果：

```
prepublish-desensitize/README.md:110
DEEPSEEK_API_KEY = "sk-faaffc04..."      ← 与 Claw/.env 在用值 sha256 完全一致
```

- 位置：一行「❌ 之前（硬编码，会被拦）」的**反面示例**里 —— 作者本意是演示"这样写会被拦"，
  却把**真实** Key 粘进去了（该文档自己就写着"`sk-placeholder`、`xxxx` 类明显占位 Key 不拦截"，
  而这里放的是完整 35 字符真值）。
- 引入时间：`7fc1920`（2026-10-09「首次纳入版本控制 —— 技能库基线快照」），**存活 3 天**。
- 唯一好消息：该仓库**尚无 remote**，从未 push → 泄露范围止于本机。

## 二、为什么这是「同一类事故的复发」

`.learnings/2026-10-09-product-repo-git-init-must-exclude-credentials.md`（已升级 R74）记录了
**同一份基线快照**把 `.neodata_token` 带入版本控制，处置是：补 `.gitignore` + `git rm --cached` + 重写历史。

那次修的是**文件名维度**（`.gitignore` 只能按路径忽略）→ 而本次泄露在**内容维度**
（`README.md` 是正常文档，任何 `.gitignore` 规则都拦不住其中的字面量 Key）。

> **`.gitignore` 是"。* 名单机制"，不是内容扫描器。** 修完文件名不等于修完内容。

## 三、取证口径（复用：禁止打印明文）

判定"是不是真凭据"必须**哈希比对**，不能靠肉眼看形态：

```
README 中的值  sha256[:32] = bf392de656301d40b05b1cd8cfa357ae
Claw/.env DEEPSEEK_API_KEY  sha256[:32] = bf392de656301d40b05b1cd8cfa357ae   ← 完全一致
```

并**用本机在用的每个凭据反向扫全仓**（`git grep -lF`）：
5 个在用凭据中**仅 1 个命中**（DEEPSEEK），另 4 个（CATROUTER/WIND/QTS/WIND_MCP_TOKEN）干净 → 范围收敛、可收口。

> 口径对齐是前提：比对用的是「值」，两侧都做 `tr -d 引号/CR` 归一，否则会出现
> "看起来不一样 → 误判为已轮换"（同 R74 系列：**比对口径不齐会给出相反结论而非报错**）。

## 五、根因与升级候选（★）

1. **守卫"存在 ≠ 接线"**：本仓**自带** `prepublish-desensitize`（含 `pre-push-hook.sh` + `scan.py`），
   但仓库**没有 `.pre-commit-config.yaml`、没有 `.git/hooks/`** → 工具从未生效。
   经验：**新增扫描器必须同时接线到"写时/推时"，并做一次可证伪自检**（我用已知正样本证实 `scan.py` 能命中第 110 行）。
2. **可升级为铁律候选**：*内容级凭据（Key/Token/密码）无法由 `.gitignore` 防护；任何"给产物型仓库加远端/对外发布"动作，
   必须先跑内容级扫描并对本机在用凭据做反向比对（哈希口径对齐），命中即阻断。*
3. **副作用提醒**：`scan.py` 会把文档里演示用的 PEM 私钥头（"BEGIN … PRIVATE KEY" 那一行）
   判为 🔴（误报）—— 本次写这份 learning 时，连 Claw 自带的 `detect-private-key` pre-commit 钩子
   都因此拦下了我的提交，**守卫确实在工作**。接钩子前需处理这类文档示例，否则会诱导使用 `--no-verify` 而失去保护。
4. **本次新的操作教训**：首次定位时用了 `git grep -nE`（**打印整行**）→ 真值落进会话记录。
   正确姿势：先 `git grep -l` 只取文件名，确认范围后再用掩码/哈希核对。
