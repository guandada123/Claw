# 容器时区 ≠ 应用时区：看到 UTC 环境不能推断"调度错位"

**日期**：2026-08-31
**场景**：统一巡检中枢 run#43，复检 run#42 修复是否生效
**等级**：★升级候选 ×2
**结果**：一次 P0 误判被自己推翻，未污染飞书通道

---

## 一、差点发生的误报

取证链走到第 4 步时，我看到两条线索：

1. `docker exec quant-strategy date` → `15:40:45 UTC`（容器 TZ 未设，默认 UTC）
2. `registry.py` 里写着 `hour=15, minute=10`，注释明写「**收盘时段任务(15:00后)**」；`hour=9, minute=0` 注释「**盘前任务(09:00前)**」

**当时的推断**：容器 UTC + cron 写 15 点 → 日行情刷新实际在北京 23:10 跑；「智能选股（盘前）」实际在北京 17:00 跑 = **收盘后才选当日标的，选股信号永远滞后一个交易日** → 定性 **P0 业务缺陷**，准备推飞书。

**这个推断是错的。** 在推之前我补做了一次验证，发现：

```python
# strategy-service/services/scheduler/engine.py
AsyncIOScheduler(..., timezone="Asia/Shanghai")           # :27
CronTrigger(hour=h, minute=m, timezone="Asia/Shanghai")   # :49
IntervalTrigger(minutes=m, timezone="Asia/Shanghai")      # :78
```

调度框架**自己带了时区**，与容器 TZ 无关。实测下次触发：

| job | cron | 下次触发（含时区） |
|---|---|---|
| 智能选股(盘前) | 09:00 | `2026-09-01 09:00:00+08:00` ✅ |
| 日行情刷新 | 15:10 | `2026-09-01 15:10:00+08:00` ✅ |
| 收盘归总 | 15:20 | `2026-09-01 15:20:00+08:00` ✅ |
| AI复盘 | 15:30 | `2026-09-01 15:30:00+08:00` ✅ |

**调度完全正确，P0 降级为 P2。**

## 二、真问题（P2）：存储时区与业务时区不一致

调度时区对了，但**代码里的时间戳没跟过来**：

```python
# jobs.py:446 大盘快照
ts = datetime.now()   # 容器内返回 UTC 裸时间（无 tzinfo）
db.execute(text("INSERT INTO index_snapshots (..., recorded_at) VALUES (..., :ts)"), {"ts": ts})
```

`recorded_at` 是 `timestamp without time zone`（不带时区），存进去的是 UTC 裸值。

**实测**：表内两批数据 `recorded_at = 15:02:36 / 15:32:35`，实为 UTC = **北京 23:02 / 23:32**，与「每 30 分钟 + 22:32 重启后跑两次」完全吻合 —— 这是**反证**，也正是坐实了「调度对、存储错」。

**影响边界（必须算清楚，不要笼统说"差 8 小时"）**：

| 北京时间区间 | 对应 UTC | 日期是否错位 |
|---|---|---|
| 00:00–08:00 | 前一日 16:00–24:00 | ⚠️ **归到前一天** |
| 08:00–24:00 | 当日 00:00–16:00 | ✅ 一致 |

A股交易时段 09:30–15:00（北京）= 01:30–07:00（UTC），**落在一致区间，业务数据不受影响**。
只有**凌晨跑的 interval 任务**（大盘快照每 30min、健康检查每 60min）会归错日期，而这些时段数据本身不变，价值低。→ **P2，不紧急**。

修法（未执行，交用户）：`docker-compose.yml` 给 strategy-service 加 `TZ: Asia/Shanghai`，一次性修好调度+存储+日志三处。**但不预置改动**（见下）。

## 三、教训（★升级候选）

### 教训 1：容器时区 ≠ 应用时区，是两个独立配置层

**看到 `TZ` 未设就推断"应用全在 UTC 跑"是脑补。** 现代框架（APScheduler / Django / Spring）普遍自带时区配置，且**通常比容器 TZ 更权威**，因为它才是业务语义的承载者。

**判据顺序**（在容器里查调度，按此顺序）：
1. 查框架自身的 timezone 配置（`grep -n "timezone" <scheduler>/engine.py`）
2. 查 `next_fire_time` 的 **tzinfo 后缀**（`+08:00` 才算数，光看小时数没用）
3. **最后**才看容器 TZ

**`next_fire_time` 是否带 `+08:00` 是唯一可信判据** —— 因为它绕过了所有"我以为"的中间层。

> 同源铁律：08-12「单链路日志≠全链路，禁脑补归因」。本次是其**配置层**变体：把"运行环境属性"当成了"应用行为属性"。

### 教训 2：误判的代价不对称，但**验证的代价很低**

这次误判如果推出去，代价是：飞书 P0 告警 → 用户半夜看到"选股滞后一天"的假故障 → 可能连夜重建容器 → 而重建会中断服务，**真问题是被修出来的不是被发现的**。

而推翻它只用了 **1 次工具调用**（grep engine.py 的 timezone）。

**规则：定性 P0 之前，必须找到该判定链路上的"最权威信源"并直接读它，而不是从环境变量/相邻线索推断。**

### 教训 3（复用）：数据文件 mtime 可当"表创建时间"的硬证据

本次为确认 `index_snapshots` 究竟是不是 run#42 新建的，用了：

```bash
pgq "SELECT pg_relation_filepath(oid) FROM pg_class WHERE relname='index_snapshots';"
# → base/16384/125422
docker exec quant-postgres stat -c '%y %n' /var/lib/postgresql/data/base/16384/125422
# → 2026-08-31 14:30:36 UTC = 北京 22:30:36  ← 与 run#42 建表时刻吻合
```

配合 `pg_stat_user_tables.n_tup_ins`（=16，纯 INSERT 无 UPDATE/DELETE）→ 同时拿到「表何时建」+「写了多少次」+「是否 upsert」，**三个独立维度互相印证**，比单看行数可靠得多。

PG 不记录 CREATE TABLE 时间，这是可行的替代取证路径。

### 教训 4（复用）：时区换算别用 `TZ=UTC-8` 这种把戏

我试过 `TZ=UTC-8 date -j -f ...`，输出 14:32:08 —— **错的**（它把 UTC 值当本地时间又减了一次）。
**正确做法：UTC 值 +8h 直接心算/算数**，或用 `date -u -j -f ... ` 明确声明输入是 UTC。
`docker inspect` 的 `StartedAt` 恒为 UTC，这个坑会反复踩。

## 四、本次真正交付的价值（不是那个被推翻的 P0）

推翻误判的同时，坐实了 **run#42 的修复真的上线了**：

- **时序对**：容器 `StartedAt = 14:32:08Z` = 北京 **22:32:08** > 代码最后写入 `docs/init.sql` **22:31:58**（差 10 秒）✅
  - 对比 run#41 那次：重启 21:14:47 **早于** 文件写入 21:15:44（差 57 秒）→ 加载的是旧代码。**同一类问题，方向相反。**
- **产物在**：4 张表全建（alert_rules/alerts/daily_snapshots/index_snapshots）+ `daily_quote.ma20/rsi14` 两列可空
- **数据真的进来了**：`index_snapshots` 从「769 次全部失败」→ 重启后 23:02、23:32 两次各写 8 个指数 = **16 行**，`n_tup_ins=16, upd=0, del=0`

**这才是"验收查产物"该有的样子**：不看日志说"成功"，看 DB 行数 + 时序先后 + 文件 mtime 三方印证。
