# ★教训：单位口径差会造出**假警报**，而基于假警报的"修复"比不修更坏

**日期**：2026-10-12（自主审计时）
**等级**：P2（无实际损失；但**差一步就把完好的数据改坏**）
**类型**：取证口径（单位/编码未对齐）
**状态**：已识别并挡住，无需修改

---

## 1. 现场

审计"我改过的 automation prompt 是否被后续覆盖"时，看到：

```
📊【板块】强弱层盘后刷新 | prompt 长度=1603
⏰【处置】实盘复核触发器   | prompt 长度=1911
```

而我记得自己恢复后测的是 **2530 / 3388 字节** → 第一反应：**又被截断了？**（当天我刚犯过一次
"全量覆盖把 prompt 抹成一行"的事故，所以这个方向是"合理怀疑"）

## 2. 为什么不是

- SQLite 的 `length()` 对 TEXT 返回 **字符数**；
- 我当时用的是 `len(s.encode())` = **字节数**（UTF-8 下中文 3 字节）；
- 比值 **2530/1603 ≈ 1.58**、**3388/1911 ≈ 1.77** —— 与两段文本的中英混排比例一致 ✓

⇒ **不是截断**，是**单位没对齐**。

## 3. 真正的危险在"下一步"

如果没做这道换算，接着就会去"恢复 prompt"—— 而那份 prompt **本来是完好的**，
于是：

> **基于假警报的修复，会把你原本没坏的东西改坏。**
> 它比"没发现这个问题"更坏，因为它披着"我在认真核查"的外衣。

## 4. 判据（可复用）

> **比对两个"数量"之前，先确认三件事：单位、编码、口径。**
> （与既有铁律「比对口径须对齐——算法 + 粒度 + 编码」同族，本条新增**单位**这一维。）

- 具体到长度类：`len(str)`（字符） vs `len(str.encode())`（字节） vs 数据库 `length()`（字符）——
  **三者常被混用**。
- 触发条件：看到"数字变小/变大且幅度可疑"时，**先算比值**再做结论；
  比值能对上一个可解释的比例（如 CJK 的 2~3 倍），基本就是口径差，不是内容变。
- 同族已知：哈希比对的 **算法（sha1 vs sha256）+ 粒度（整值 vs 匹配片段）** 也曾让结论反过来。
