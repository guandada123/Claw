# ★教训：CI 红了先做**归属判定**（按用例名），别默认是自己的改动 —— 一天撞上两次

**日期**：2026-10-11（同一晚两次）
**等级**：P2（不改代码，但**误判归属会导致修错东西**：要么白修自己没坏的代码，要么漏掉真问题）
**类型**：归因错误（CI 红是**聚合状态**）
**状态**：两次都正确定位到"不是我"

---

## 1. 两次现场

| # | 现象 | 顶着谁的提交 | 真归属 |
|---|---|---|---|
| ① | Security Scan 报 `scan_git_history_secrets.py:48` 含 `PRIVATE KEY` | **我的** | **1 分钟前**并发自动化新增的密钥检测脚本，其**模式串**被朴素 grep 命中 |
| ② | Unit Tests 报 `test_agents_md_has_no_volatile_memory_counts` | **我的**（一次 merge） | 并发自动化的**负向验证探针**：往 AGENTS.md 植入"完整 999 条 + 逐条证据（**植入的违规串**）" |

两次的 top-level conclusion 都写着 `failure`，而**被标记的提交都不是肇事者**。

## 2. 判定方法（可复用）

1. **别看 top-level conclusion，看 job 粒度** → 找到红的那个 job。
2. **看失败用例名**（不是只看"Unit Tests 失败"）：用例名往往**自带领域**，
   一眼能看出它测的是谁的改动（本例 `test_doc_volatile_claims` 测 AGENTS.md，
   与我的 learnings 索引改动无关）。
3. **看有没有更早的同类红**：GitHub Actions 的 run 不随分支/提交消失 →
   翻一下近几轮 run，常能直接看到"始作俑者"（本例他们自己那条
   `test(probe): 临时植入违规串…` 就明晃晃在同列表里）。
4. **确认失败清单只列了那一条**：pytest 会报**所有**失败；只有一条 → 我的用例全过。

## 3. 更要紧的一条：负向验证在飞时，**所有人的 CI 都会红**

本例②里，探针被**推到了 main**（因为要验证的正是"main 推送后 CI 的守门"），
于是窗口期内**任何**并发推送都会继承那条违规串而变红 —— 包括我那次 merge。

> **看到红之前，先问"现在有没有探针/负向验证在飞"。**
> 有 → 预期它红，别去改自己的代码；并知道它会持续到对方 revert 为止。

（对方随后 `revert(probe)` 回滚，后续 run 全部恢复 success ✓ —— 这条链路是干净的。）

## 4. 反过来说：做探针的人要预期"别人会被误伤"

- 探针推到 main ⇒ **窗口期内别人的 CI 红是预期的**，最好在提交信息里写明"本提交会红"，
  或尽快 revert（本例两者都做了）。
- 探针的**收尾**不只是 revert：还要确认**跨仓巡检**不会把它当成真故障长期挂住
  （同一天的另一篇：孤儿分支红灯会**永久**常驻）。
