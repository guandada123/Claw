# ★教训：审计别人的系统前，先读**既有的审计代码**（一次自我假警报的复盘）

**日期**：2026-10-11 晚（用户授权"后续所有判断与决策"后的首轮自审）
**类型**：分析口径错误（不是系统故障；**是审计者自己制造的故障**）
**结果**：假警报作废 + 顺手修掉 1 处真缺陷

---

## 1. 我做了什么、错在哪

审计"自动化是否静默停摆"时，我用了一条 SQL：

```sql
SELECT ... FROM automations WHERE status='ACTIVE'      -- ❌ 缺 deleted_at
```

结果报出 **20 条"排期过期"**、其中 13 条"从未运行"，我据此判定为**僵尸**，
甚至准备删 14 条、复活 2 条签到任务（以为在丢积分）。

**全是假的**：`automations` 表是**软删除**语义 —— 删除只写 `deleted_at`，
`status` 列**不随之改写**。正确口径：

```sql
WHERE status='ACTIVE' AND deleted_at IS NULL    -- ✅ 79 条活跃，排期过期 0 条
```

## 2. 最刺眼的一点

同一个口径陷阱**早就写在仓库里**了 —— `automation_failure_watchdog.py:351`：

> ⚠️ 口径注意：对账脚本按 `status='ACTIVE' AND deleted_at IS NULL` 取"活跃"。
> 只看 status 会把 20 行**已软删除**误当活跃 → 虚高到 91。

**连"20 行"这个数字都一样**。我如果先 `grep -rn "next_run_at" .workbuddy/scripts/`，
就不会重走一遍别人已经踩过并记录下来的坑。

另有一处同源陷阱：`last_run_at` **不可信**（签到任务日志里有运行记录，该列却是 NULL），
判"是否真跑过"只能看调度日志的 `run start` 事件对。

## 3. 判据

1. **审计前先读既有审计/检查代码**：它们编码了过往踩坑结论（本例：软删除口径、日志才是真源）。
   成本极低（一条 grep），收益是避免"重复劳动 + 假警报 + 误删生产配置"。
2. **口径错误会伪装成"重大发现"**：越是"20 条全坏了"这种整齐的结论，越要先怀疑自己的过滤条件。
3. **写库/删库类动作前必须交叉验证**：若我直接对 DB 动手（本系统禁止），20 条配置会被误删。
   本例唯一的安全网是"所有自动化变更必须走 `automation_update` 工具"——工具对软删除记录
   直接回「already deleted」，**挡住了这次误删**。这条约束值得保留。
4. **顺手修掉的真缺陷**：`health_check.py` 的"活跃自动化数"也用了旧口径 →
   健康报告长期虚高（99 vs 真实 79）。已修。

## 4. 同族

- 「`grep -c` 返回 0 时先验证模式本身能命中，再信'查无此物'」—— 同一族：**先验证口径，再信结论**
- 「聚合值稳定 ≠ 状态稳定」—— 本例是"聚合值虚高"的变体
- 「数量骤降优先怀疑口径，而非康复」—— 反向同理：**数量异常也优先怀疑口径，而非发现**
