# ★教训：写死日期的测试会「**本地恒绿、CI 恒红**」—— 比"8 小时窗口必红"更坏的一种时区坑

**日期**：2026-10-11（新写的测试上线即把 CI 判红）
**等级**：P2（不造成数据问题，但**只在 CI 暴露的失败**会让本地验证完全失效）
**类型**：time-dependent test（恒红形态）
**状态**：已修（`a631c5e`），并把**验证方式**一并改掉

---

## 1. 现象

新写的测试断言：

```python
assert last.startswith("2026-10-09")
```

本地（+08）**905 全过**；CI 的 Unit Tests **判红**。CI 实际得到的是：

```
AssertionError: 2026-10-08 23:30
```

同一时刻，但 **CI runner 是 UTC、本机是 +08** → `1791502200` 在 UTC 下是 `10-08 23:30`。

## 2. 与本仓已知时区坑的区别（为什么值得单独记）

| | 已知坑（`test_contract.py`） | 本次 |
|---|---|---|
| 形态 | **每日 8 小时窗口**必红（UTC 16:00~24:00） | **恒红** |
| 本地能否发现 | 特定时段能撞见 | **永远看不见** |

"恒红"更坏：本地无论什么时候跑都是绿的，**唯一的反馈渠道就是 CI**，
而 CI 是异步的 —— 极易被当成"环境问题"糊过去。

## 3. 修法

**① 断言**：不写死日期，按**与生产同一套本地时区换算**重建期望值再比：

```python
want = datetime.fromtimestamp(1791502200).strftime("%Y-%m-%d %H:%M")
assert last == want
assert last.startswith("2026")   # 另加一条与时区无关的粗判
```

顺带钉住"毫秒口径"（若误把毫秒当秒解，会得到公元 5.8 万年那种值，比不过）。

**② 验证方式（更重要）**：在本地**复现 CI 条件**再跑 ——

```bash
TZ=UTC python -m pytest tests/ -q      # → 908 passed，且证明无其它时区敏感用例
```

> 只修断言不修验证方式，下次还会踩。

## 4. 可复用判据

> **测试里出现的任何"绝对时间/日期字面量"，都要问：它在 UTC 下还是同一个值吗？**
> 更要紧的是：**这类失败本地看不见** → 写日期相关断言时，验证必须用 `TZ=UTC` 跑一遍。

同族已知：容器 TZ=UTC + naive `now()` 导致凌晨落库日期错位（2026-08-31 / 09-01 两篇）。
