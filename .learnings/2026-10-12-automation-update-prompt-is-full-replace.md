# ★升级候选：`automation_update` 的 prompt 是**全量覆盖**，不是补丁 —— 我差点把一份 2370 字节的 prompt 抹成 1 行

**类型**：工具语义误用（字段是全量替换，被我当成增量修改）

## 1. 事故经过

改 PA-016 时，我只想改 prompt 里的**一行**（`[频率] 交易日 15:30` → `15:20`）。
于是传了：

```python
automation_update(mode="update", id=..., rrule=..., name=...,
                  prompt="[频率] 交易日 15:20（收盘后；...）")   # ← 只有这一行
```

返回的 `automation.prompt` **只剩那一行** —— 原 prompt 的 2370 字节
（角色/输出/权限/背景/Step 1-2/结果处理/铁律）**全没了** ✗。

## 2. 为什么没造成损失

**因为我按 RRULE 技能的要求先导出了原 prompt**：

```bash
sqlite3 ~/.workbuddy/workbuddy.db "SELECT prompt FROM automations WHERE id='<id>';" > /tmp/pa016-<id>.txt
```

出事后 1 分钟内用该文件**全文回填 + 只改目标行**，再用 `diff` 逐字节校验：
**只有第 4 行不同** ✓，其余字段（name/rrule/status，含 `next_run_at` 被平台重算）均正确。

## 3. 判据（可复用）

> **改 `automation_update` 的任何字段前，先把它「原样导出」到临时文件；
> 传参时必须传「改完之后的全量内容」，而不是"只传改动部分"。**

- 这是**覆盖式 API**（同 `mode=update` 的其它字段同理：name/prompt/rrule 都是整值替换）。
- 导出还有一个副作用好处：**diff 校验**（"只有目标行变了"）—— 这正是该技能里
  「回读 DB 逐字节 diff 校验」那一条的落地方式。
- 与既有铁律同族：**"同一语义的值必须单一真源"** —— 改之前先拿到真源，别凭记忆重写。

## 4. 同族提醒

- 本仓另一处同类坑：`registry.json` 的字段写入也是**整值替换**（所以要用
  `discovery_schema.save_registry_atomic` 而不是手写 JSON）。
- 凡是"改一个字段"的操作，先问一句：**它是补丁语义还是替换语义？**
  替换语义下，少传的部分 = **被删除**，而不是"保持原样"。
