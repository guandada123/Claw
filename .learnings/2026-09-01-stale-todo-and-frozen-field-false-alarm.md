# 巡检产出物本身也要被验证：幽灵待办 + 差点误报 P0

日期：2026-09-01（统一巡检中枢 run#47）
等级：P2（无故障，但连续 8 轮产出误导信息）

## 事实

### A. 幽灵待办：一项待办被沿用了 8 轮，其实早就修好了

「19 个自动化 prompt 裸 source」这条待办从 run#40 一直沿用到 run#46，7 轮里每轮都复述一遍。
本次核查发现两个问题：

1. **计数错**：实际是 **50 个 ACTIVE + 3 个 PAUSED**，不是 19。
2. **状态错**：该问题已于 **08-31 08:03** 根治 —— 把 `export CLAW=...` 写进了 `~/.zshenv`。
   zsh 是唯一「任何调用方式都会读」的启动文件，`.zshrc`/`.zprofile` 只覆盖交互/登录 shell，
   所以非交互的自动化 runner 之前会间歇性拿到空的 `$CLAW`。

取证（关键，别只看注释）：
```
env -i /bin/zsh  -c 'echo ${CLAW:-UNSET}'   # → /Users/guan/WorkBuddy/Claw  ✅
env -i /bin/bash -c 'echo ${CLAW:-UNSET}'   # → UNSET                        ⚠️ 残留边界
env -i /bin/zsh  -c 'source $CLAW/.workbuddy/scripts/automation_preamble.sh; echo $? $SCRIPTS'
                                            # → 0 /Users/guan/WorkBuddy/Claw/.workbuddy/scripts ✅
```
runner 实际用 zsh → 50 个裸 source 全部安全。残留边界：干净环境的 bash 仍 UNSET，
若将来 runner 换成 bash 会重新暴露，届时的加固才需要动 prompt（本次未动）。

### B. 差点误报 P0：一个冻结字段看起来像「63 个自动化集体停摆 2.5 天」

`workbuddy.db` 的 `automations.last_run_at` 自 **08-29 21:30** 起冻结，全表最大值 08-29 21:29:46，
而当时是 09-01 04:03。若据此定性就是 P0。

**查消费者后推翻**：`automation_health.py:140-159` 已在 08-31 用
`max(last_run_at, automation_runs 最新派发记录)` 做了校正，并把字段滞后降级为
「诊断标注，不改健康色」。实跑确认 `critical=0 / healthy=58`。

滞后分布 24h–168h（52/63 项）是平台已知行为：**只在 PENDING_REVIEW 等终态回写 last_run_at，
ACCEPTED 自动执行不回写**。同表里 `next_run_at` / `updated_at` 是活的，可用来反证调度正常。

## ★ 升级候选

### 1. 沿用待办必须先做「还成不成立」的验证，不能只复述
巡检清单里每一条**跨轮沿用**的待办，本轮开工时至少要花一次调用确认它还活着
（查修复提交 / 查配置文件 mtime / 实跑一次）。
**待办清单没有「已修复自动下架」机制 → 它会腐化成噪音源，且腐化后没人看得出来。**
本次是 8 轮，如果不管会变成 80 轮。

### 2. 计数类待办要定期重算，别沿用旧数字
19 → 50。写待办时的查询条件（可能只扫了某个子集、或当时 ACTIVE 数不同）
会随着时间失效。**数字型事实的半衰期比布尔型事实短得多。**

### 3. 发现「某个字段异常」时，先找它的消费者，再定级
与 run#45「缺表先查写入方」同源：**孤立看数据源没有意义，要看数据流两端。**
差别在于这次反过来了 —— 不是「没人写」而是「有人补偿」。
判据：先 `grep -rn "<字段名>" <脚本目录>` 找消费方，读它有没有兜底/校正逻辑，再决定要不要告警。
本次如果直接推 P0，用户会在凌晨 4 点看到一条「63 个自动化全停摆」的假故障。

### 4. 用同表内活字段交叉反证，别只盯一个指标
`last_run_at` 死了，但同表的 `next_run_at`（09-01 04:03:22，与真实触发时间吻合）
和 `updated_at`（03:03:22，每小时更新）是活的。
**同一张表里字段的「存活度」可能完全不同，用一个死字段否定一张活表是常见误判。**

### 5.（附）同一份数据两种入参格式，必须在入口归一化
同轮顺手修掉的真 bug：`push_card.py` 的 JSON 模式原样透传 `table`，只有 CLI 模式才
`split("|")`。我按 CLI 习惯传 `"a|b|c"`，`for row in rows` 把**每个字符**当成一列，
飞书卡片表格渲染成一地碎字（已发卡片实证，后用 `messages patch` 就地修正）。
**多入口（CLI / JSON / SDK）共用一个内部函数时，格式差异必须在最外层归一化 + 校验，
否则只会静默产出垃圾而不是报错。** 已加 `_normalize_table()`：两种写法都收，列数不符告警并补齐。

## 复用写法

- 判「非交互 shell 能否拿到某变量」：`env -i /bin/zsh -c 'echo ${VAR:-UNSET}'`。
  zsh 读 `~/.zshenv`（任何调用方式都读），bash 非交互读 `$BASH_ENV`，两者不同。
- 判「调度到底有没有跑」的优先级：`automation_runs` 派发记录 > `next_run_at` 是否推进 >
  `last_run_at`（最不可信）。
- 待办去腐的最小动作：每轮把沿用待办过一遍，标 ✅已下架 / 🔴根因定位 / ⏳仍在，附一行判据。
