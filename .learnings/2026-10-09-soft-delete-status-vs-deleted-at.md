# ★升级候选：软删除语义 —— 判「自动化是否活着」必须 `status` 与 `deleted_at` 一起看，只看其一必错

**日期**：2026-10-09（盘点自动化健康度时踩到；同日在同一件事上连续错 3 次）
**等级**：P1（我据错误口径编造出一个**不存在的问题**，并把它上报给用户要求人工处置）
**类型**：correction（取数口径错误，非逻辑错误）
**状态**：已修正脚本 + 已撤回错误结论；规则候选

---

## 1. 事实（实测）

`workbuddy.db` 的 `automations` 表是**软删除**语义：

| status | deleted_at | 条数 | 含义 |
|---|---|---:|---|
| ACTIVE | 空 | **71** | ✅ 真正活跃 |
| ACTIVE | **非空** | **20** | ❌ **已软删除**（status 列不会被同步改写） |
| DELETED | 非空 | 36 | 已删除 |
| PAUSED | 空 | 1 | 暂停 |
| PAUSED | 非空 | 54 | 已删除 |

**权威口径 = `deleted_at IS NULL`**，与 `hub_reconcile.py` 的 `live = rows if not deleted_at` 一致
（它报 `observed_live=72` = 71 ACTIVE + 1 PAUSED，✅ 自洽）。

那 20 行的 `deleted_at` 时间戳恰好落在它们最后一次运行之后 —— 是**正常的历史删除**，不是异常残留。

## 2. 我的误判链（三次，同一件事）

| # | 我的结论 | 错的环节 |
|---|---|---|
| 1 | 「15 条自动化 `next_run_at` 过期 → 疑似 stale」 | SQL 只写了 `status='ACTIVE'`，**没写 `deleted_at IS NULL`** |
| 2 | 「14 条僵尸自动化待停用」 | 执行时 `automation_update` 报 `not found` → 我得出的解释是"平台侧删了、DB 没同步" —— **编造了一个机制**，而真相是"它们本就已删除" |
| 3 | 「20 条幽灵行，污染计数，需人工清理」 | 把 2 的编造结论包装成"数据卫生问题"上报用户，建了抑制清单去绕开自己的 bug |

**每一步都在为前一步的错误找解释，而不是回头怀疑自己的取数口径。**

## 3. 元教训（本条真正要固化的东西）

> **数据"看起来像 bug"时，先怀疑自己的取数口径，再怀疑系统。**

三条具体动作：
1. **别只看一列下定论**。本表的"是否活着"是**两个字段的合取**（`status` + `deleted_at`）。
   凡下"有多少条 X"的结论前，先 `SELECT 关键列组合, COUNT(*) GROUP BY` 把**交叉表**打出来 ——
   本次只要打一次交叉表，20 行的真相立刻暴露（我直到第三轮才做这件事）。
2. **"工具找不到"有两种解释，别急着选最戏剧的那一个**。`automation_update` 返 `not found`，
   第一解释应是"它确实已被删除"，而不是"平台与 DB 不同步了"。选后者会导向一连串虚构。
3. **发现自己需要为绕开某现象专门加一套机制时，先怀疑那个现象本身**。
   我为了压住"20 条幽灵行"写了 `automation_known_phantoms.json` 抑制清单 ——
   **机制的存在本身就是信号**：一个健康系统不需要为"已删除的记录"专门建抑制表。

## 4. 附带的第二个取数错误（同源）

对账脚本首版用 `": run start:" in line` 判日志事件类型 → **恒为 false**，
因为日志实际是 `...Scheduler] run start: id=`，`]` 与 `run` 之间是「] 」而非「: 」。
后果：`starts` 恒为 0 → **83/91 被判成僵尸**。
修法：改用正则捕获组判类型。

**两次错的都是"取数与匹配口径"，不是判断逻辑。** 所以防复犯的重点也应放在口径上。

## 5. 已修正

  移除全部"幽灵行抑制"机制（那是在绕开自己的 bug）；输出中**显式列出被排除的软删除行数与裸 status 计数**，
  让后人一眼看到"91 是虚高值"。
- 撤回 `.learnings/2026-10-09-active-rows-may-be-platform-phantoms.md`（已移废纸篓，防周日被升为错误铁律）。

## 6. 去重

- 与铁律「🔴 数量骤降优先怀疑口径，而非康复；『条目数』≠『问题数』」**互为镜像** ——
  那条讲"数量掉下来先怀疑口径"，本条讲"**数量看起来多出一批怪东西时，同样先怀疑口径**"。
  两条可合并表述为：**数量出现异常（升或降）时，第一动作是打交叉表核对口径，而非解释现象。**
- 与铁律「🔴 同一语义的值必须单一真源；『已配置』≠『被读取』」同族：本条是"同一状态由两列表达，
  必须合取判断"。
