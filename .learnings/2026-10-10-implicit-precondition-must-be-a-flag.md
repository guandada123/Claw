# ★升级候选：判据带「隐含前提」时，必须在接口层表达出来 —— 否则任何跨档位复用必然自造假红

**日期**：2026-10-10（03:30 记忆维护自动化借用了 04:00 的新脚本后触发）
**等级**：P2（产生"每天 22/24 小时必然报红"的假警，并**差点被记成"索引静默失败"**）
**类型**：correction（接口设计缺陷，非逻辑错误）
**状态**：已修复并复验

---

## 1. 现象

2026-10-09 新建的 `memory_index_selfcheck.py`（「🗂️ 记忆索引重建」每日 04:00 的步骤 2）
把年龄阈值硬编码为 `MAX_AGE_HOURS = 2.0`。

2026-10-10 03:30，**另一条自动化**（「🧹【记忆维护】记忆+上下文维护」）**自行发现并借用了该脚本**
（**其 prompt 从未引用我** —— 是运行它的 LLM 探索到了），于是报：

> 🔴「索引过期 5.04h > 2.0h（重建可能静默失败）」

**根因**：那 2h 阈值的**隐含前提是"我刚重建完（索引龄只有几秒）"**。
而重建是**每日一次** → 除 04:00–06:00 之外**任何时刻**跑该脚本，索引龄都 > 2h → **22/24 小时必然报红**。

## 2. 它为什么没酿成事故（值得记下来）

**借用方（03:30 自动化）自己诊断对了**，写进 Claw 日日志：

> 该 2h 阈值的设计语境是「刚重建完」…除 04:00–06:00 之外任何时刻跑都必然报红（22/24 小时）
> 判定：**预期非故障**，**不据此报警**
> 教训：判据带**隐含前提**（"我刚重建完"）时禁止跨档位复用 → 同族于 Step 0.22（跨文件借词 = 自造假红）

→ **它没有产生假推送**。缺陷是我的，处置是它的。

## 3. 修复：把隐含前提搬到接口上

| 调用姿势 | 阈值 | 语义 |
|---|---|---|
| **默认** | **26h**（= 24h 周期 + 2h 余量） | 周期感知 —— **任何时刻调用都安全** |
| `--after-rebuild` | 2h | **仅当刚跑完重建**时用（抓"重建静默失败"） |
| `--max-age-h N` | 显式覆盖 | 特殊场景 |

并在严格模式的失败文案里加**自诊断提示**：
「⚠️ 若本次并非紧接重建之后，请去掉 `--after-rebuild`（该阈值为'刚重建完'设计）」
—— 让**将来的误用能自己说出病根**。

复验：默认模式 → ✅ exit 0；`--after-rebuild` 在非重建时刻 → 🔴 exit 1 且带提示；
v5 prompt 回读后逐字重跑 → 两步 `exit=0`（年龄 0.0h / 模式"严格·刚重建完"）。

## 4. 防复犯（规则候选）

> **判据若带隐含前提（"我刚做完 X"、"我是被 A 调用的"、"此刻是 T 时段"），必须在接口层显式表达成参数，不能靠"调用方应该知道"。**

三条可执行动作：
1. **默认值必须对最宽泛的调用方安全**；严格判定要做成**显式 opt-in**。
   （反例即本条：把"仅适合刚重建后"的阈值设成了默认值。）
2. **写进脚本 docstring 的第一屏**：说明"本判据的设计语境是什么、什么情况下不该用它"。
   本次修复同时把这条写进了 04:00 自动化的 prompt 铁律 ④(e)。
3. **让误用可自诊断**：失败文案里直接给出"你是不是用错了"的提示与纠正动作，
   而不是只报"指标超标"。

## 5. 去重

- 与铁律「🔴 校验/占位符/安全检测必须下沉到被复用的内层函数」**同族**：
  那条讲"校验要下沉"，本条讲"**下沉之后，被复用者自身的适用前提也必须一并下沉到接口**"
  —— 否则复用越方便，误用越必然。
- 与铁律「🔴 检测器阈值须用正常基线标定」（本机 Step 0.17）**同族**：
  本条是它在"跨组件复用"场景下的又一次复现。
- 与本机既有条目 `2026-10-09-manual-run-pass-is-not-scheduler-run-pass`（手动跑通过 ≠ 定时环境通过）
  **互补**：那条讲"验证要换上下文"，本条讲"**判据本身也要声明它的上下文**"。

## 6. 元教训（本次审计最值得记的一点）

该缺陷**不是我自己发现的**，是**另一条自动化的 LLM 把它写进 Claw 日日志**后，我在审计时才读到。
→ **我方组件的缺陷，可能只被非我方组件记录。审计必须读跨组件的日志**，不能只查自己的产物。

## 7. 同日第二例（同族）：`>30KB` 绝对阈值 → 基线相对

**这是同一个根因的另一个实例，由同一条 03:30 自动化诊断（它写进了 Claw 10-10 日日志）。**

### 7.1 现象与证据

「记忆维护」1c 判据原为「**绝对** >30KB 的自动化 memory 计数」。实测该计数**结构性失效**：

- **结构根因**：`rotate_automation_memory.py` = 保留 14 天 + 30KB 门槛 → **稳态体积 ≈ 14 × 该档日增量**。
  watchdog 日增 ≈6.4KB → 稳态 ≈90KB，**本身就 >30KB**。
- **锯齿实测**：逐日计数 `2 → 6 → 10 → **1**（周归档日骤降）→ 3 → 3 → 8 → 14 → **15**`。
  「归档日归零、随后单调回升」是**参数决定的必然形态**。
- 结论：恒在的 🔴 每天进报告 → **训练读者忽略红色**（本机铁律：告警价值 = 症状准 × 药方对）。

**关键判断：改数字没用。** 固定绝对阈值必被反复越过 → 必须改为相对该档**自身基线**的判定
（即 Step 0.17「检测器阈值须用正常基线标定」）。

### 7.2 处置

新建 `~/.workbuddy/scripts/automation_memory_health.py`：
- 每档维护最近 30 天体积历史（写 `automation_memory_baseline.json`）
- 判据**全部相对自身历史**：日增量 > max(3×自身中位, 5KB) → ⚠️；> max(8×自身中位, 25KB) → 🔴；
  单日 +50% → 🔴；**体积绝对值不作判据**（只列 Top5 供记录）
- 历史点 < 3 → 「基线建立中」**不判定**（防新档一上线就报红）

反向验证（合成目录 + 注入历史，四档）：`steady` 不报 ✅｜`warn_band` ⚠️ ✅｜`crit_band` 🔴 ✅｜`surge` 🔴 ✅

**归档器参数不动**（2e 的 14 天契约不变），只换 1c 的判据 → 两条职责重新清晰：
**2e 负责"把体积压下去"，1c 负责"判增长是否异常"。**
1c 段与 2e 的交叉引用说明已随本次一并写入 prompt。

### 7.3 顺带验证出的一条「改 6KB 系统 prompt」的安全作业法

「记忆维护」prompt 有 6.7KB，此前两次因**转录风险**回避修改。本次用三步把风险降到可接受：

1. **先备份**：从 DB 读出原文存成文件（本次 6,693 字符 → 存 `automation-backups/`）
2. **改完 diff**：把改后 prompt 与备份做 `difflib` 逐行比对，**列出全部差异块并断言每块都在预期范围内**
3. **端到端跑**：在真实 cwds + preamble 环境里跑改后的命令，看退出码

本次 diff 结果：4 处差异 = 版本号（v11→v12，预期）+ 1c 段（预期）+ 2e 交叉引用（预期）
+ **一条分隔线长度差（71→59 个 `━`）**。
最后一项**属实、非预期但纯视觉**：经核实两侧语义内容均为空、且无任何脚本解析该分隔线。
**如实记录而非宣称"零意外改动"** —— 这也是本条教训的一部分。

### 7.4 同族性

：**判据/阈值的"适用前提"与"标定基线"必须显式化**：
- §3 那例：前提「我刚重建完」→ 做成 `--after-rebuild` flag
- §7 这例：基线「该档自身的正常日增量」→ 做成基线历史文件
两者都拒绝"靠调用方/读者心知肚明"。
