# 修上游 ≠ 修链路：一次「一条链路三层静默失效」的取证

- **日期**：2026-10-09
- **级别**：P1（产出恒空且无告警；消费方本可发现却未发现）
- **来源**：统一巡检中枢候选 `disc-20261009-06` 落地（用户「全部授权」）
- **关联既有铁律**：「数据层/HTTP 调用禁止静默吞非 200 响应」「上游定时任务失败 → 下游静默产出旧结论」「日志成功 ≠ 数据落库」「搜到 ≠ 验完」

## 一、事故形态

候选只报告了**一个**问题：「`cron_monitor.py` 的 `fetch_bond_10y_yield` 恒返回空列表」。
实测发现是**三层叠加**，只修被报告的那一层，收益 = 0：

| 层 | 事实 | 若只修它 |
|---|---|---|
| L1 数据源 | `fetch_bond_10y_yield` 无条件 `return []` | 仍取不到数据（L2 坏） |
| L2 对侧数据 | `fetch_csi300_daily` 依赖的东财 `push2his` 接口 ut token 已失效（实测 `rc=102`/`data=null`）→ 静默 `return []` | 仍算不出相关性（L1 坏） |
| L3 消费方 | `check_stock_bond_correlation` 全库**零调用方**（死代码） | 两个源都修好，函数仍永不执行 |

## 二、取证方法（可复用）

「某函数是否死代码」只认**全库符号检索**，不认「我在某处没看到调用」：

```bash
grep -rn "<函数名>" --include="*.py" . | grep -v .venv
# 只命中定义行 → 死代码
```

「数据为空」应三分：**源不可用 / 源可用但无数据 / 面板改版解析失败**。
本修复把三者压成两个出口，让消费方无法把它们混为一谈：

- `(None, "原因")` — 取数失败（网络 / HTTP / 解析），调用方**必须**显式处理
- `([...], None)` — 取数成功（列表可能为空）

## 三、踩到的解析陷阱（已被单测钉住）

chinabond `historyQuery` 返回的页面里，**第一个 `<table>` 是查询表单**，
其表头同样含「曲线名称」「10年」两个关键词 —— 若按「找含关键词的表头行」定位，
会命中表单表格，把「3月」列当成「10年」列读出：**全程不报错，只出错数**。

修法：**从后往前**遍历表格，要求表头同时含「曲线名称」+「日期」+「10年」，
且**能真正提取到数据行**（`if series: return`）。
回归用例：`tests/test_stock_bond_correlation.py::test_parse_filters_target_curve_and_skips_missing_value`

## 六、规则候选（待周度升级评估）

- ★ **修上游 ≠ 修链路**：修复「数据恒空」类问题时，必须沿链路
  **向上一步**（数据源是否真的可达）与**向下一步**（消费方是否真的存在/被调用）各验一次；
  只修被报告的那一层，收益 = 0。
- ★ **解析第三方 HTML 前先确认「第几个表格是数据表」**：查询表单常与数据表同页且表头相似；
  定位条件必须包含「能提取到数据」这个必要条件，而非仅匹配关键词。
- **注释里的外部阻塞会过期**：代码注释声称的第三方阻塞（架构不兼容 / 接口下线），
  在被引用为决策依据前必须复测。
