# ★升级候选：手动跑通过 ≠ 定时环境通过 —— launchd 中的 `python3` 读不了可移动卷，守卫首次实跑即误报 CRIT

**日期**：2026-10-09（建立 `wb-ssd-guard` 宿主盘挂载守卫时首次踩到）
**等级**：P1（守护逻辑在真实运行环境下误报最高级别 + 写下告警标记，属"守卫自己先坏"）
**类型**：correction（验证口径错误）
**状态**：已修复 + 已复验；规则候选

---

## 1. 现象

新建 `wb-ssd-guard`（宿主盘挂载守卫，launchd 每 30 分钟跑一次）。四个检查项：

| 检查 | 手动实跑（终端） | **launchd 实跑** |
|---|---|---|
| mount（`/Volumes/ZHITAI` 是否挂载） | ✅ ok | ✅ ok |
| symlink（两条软链是否完好） | ✅ ok | ✅ ok |
| **files（4 个关键文件是否可读）** | ✅ ok | 🔴 **crit：4 个全 `PermissionError`** |
| space（使用率） | ✅ ok | ✅ ok |
| **总判定** | **🟢 OK（exit 0）** | **🔴 CRIT** → 写了 `~/workbuddy-ssd-ALERT.txt` 告警标记 |

同一份代码、同一台机器、同一个解释器（`/usr/bin/python3` 3.9.6），只因为**调用上下文不同**（终端 vs launchd），结果相反。

## 2. 根因

macOS **隐私策略（TCC）**不授予 launchd 启动的 `/usr/bin/python3` 读取**可移动卷**（`/Volumes/*`）内容的权限。
而 `~/.workbuddy` 是软链 → `/Volumes/ZHITAI/workbuddy_data`，于是对其中任何文件 `open()` 都抛 `PermissionError`。

关键点：
- 手动跑时终端进程（及其子进程）**继承终端已有的授权**，所以读得到 → **手动测试给出的是假绿灯**。
- 目录级操作（`os.path.ismount`、`shutil.disk_usage`、`os.listdir`）**不受该限制**，所以 mount/space 两项照常通过 —— 这更掩盖了问题：4 项里 3 项绿，很容易被当成"偶发"。

## 3. 处置

1. **存在性判定改 `os.stat()`**（走目录项，不触发 TCC 内容访问限制）→ 缺失=crit，可继续工作。
2. **`PermissionError` 降级为 `warn`** 并显式注明「受 macOS 隐私策略限制，**非数据故障**」—— 绝不误报 crit。
3. **删掉内容读取**：因为**文件内容级校验本就有归属** —— 03:30「记忆+上下文维护」自动化在**应用进程内**运行（应用有完整磁盘访问权限），本来就检查 MEMORY.md 的可 grep 性。守卫只管**宿主层三件事：挂载 / 软链 / 空间**（这三项在 TCC 下不受限）。职责分离后，既无覆盖缺口，也无多余的权限依赖。
4. **复验**：`launchctl kickstart -k` → `last exit code = 0`｜jsonl 最新一条 `overall = ok`、四项全 OK｜误报标记已删除。
5. 把本条教训写进守卫脚本自身的「铁律」注释（第 ⑤ 条）与 `--selftest` 场景 ④b，防后人改回去。

## 4. 防复犯（规则候选）

> **定时/守护类逻辑的验证，必须在真实执行环境下实跑并读回结果；"手动跑一遍通过"不构成验收。**

三条硬性动作：
1. **验收口径**：凡交付定时任务（launchd / cron / 平台自动化），验收证据必须是**该调度器实际触发的那一次**的输出（`launchctl print` 的 `last exit code` + 组件自己的日志），不得用手动执行代替。
2. **优先选不依赖权限的判据**：能 `stat` 就不要 `open`；能查目录项就不要读内容。**权限边界会随执行上下文变化**。
3. **守护逻辑必须有「自己坏了」的判据**：本守卫若照原样上线，会在 SSD 正常时持续误报 CRIT（假警报 → 用户很快学会忽略 → 真故障也被忽略）。凡守护/探针，必须自问：**"它有没有可能因为自身环境问题而误报？"** 并把权限受限这类"非数据故障"降级为 warn 而非 crit。

## 5. 去重

- 与铁律「🔴 监控/取证/告警类任务不得跑在被观测对象上」同族（都是**观测者与被观测环境的关系**问题）。区别：那条讲"观测者不能依赖被观测对象存活"，本条讲"**观测者所处执行上下文会改变其判定能力**"。
- 与铁律「🔴 验证 `trap EXIT` 清理必须另起一个 shell 调用」同源（都是"同环境自测会给出假绿灯"）。建议合并表述为：
  **「凡涉及执行上下文（shell / 调度器 / 权限域）的验证，必须换到目标上下文再测一次。」**
