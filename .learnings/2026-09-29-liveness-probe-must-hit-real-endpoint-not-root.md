# 存活探针打了根路径：把「静态页 200」当成「API 已恢复」，误判修复 3 天

**日期**：2026-09-29（公众号精读槽位2 上游复核时发现）
**等级**：P1（导致连续多日给出与事实相反的「已恢复」结论，掩盖真实故障）
**状态**：已定性（故障本体=云 RSS 凭证 401，待用户处置）

---

## 1. 现象

下游「公众号精华」精读自 2026-08-13 起每天 `read=0`（47 天）。逐日复核上游时：

- **09-25**：记录「云轨 `wechatrss.waytomaster.com` HTTP **401** 无效认证凭证」
- **09-26**：记录「云轨**已从 401 恢复为 200**（唯一好转项）」
- **09-27 / 09-28**：沿用「云轨 HTTP 200，自 09-25 恢复后持续正常」

连续 3 天把云轨判为「正常」，故障归因全部落在本地 `localhost:5001` 登录态上。

## 2. 根因：探针口径错位

复核时用的命令是：

```bash
curl -s -o /dev/null -w "HTTP=%{http_code}\n" https://wechatrss.waytomaster.com/
```

打的是**站点根路径**。该服务根路径是静态页，**恒返回 200**，与业务是否可用无关。
真实业务端点从未被探过。今天按真实调用链实测：

```
sync_wx_articles.py → wx_rss_auth.get_subscriptions()
  ⚠️ 订阅列表接口 HTTP 401: {"detail":"无效的认证凭证"}
  → {'subscriptions': []}   # len=0，无文章可拉
```

**故障从 09-25 至今根本没恢复**，且凭证 `~/.workbuddy/auth/wx_rss_api.sh`
（`WX_RSS_API_KEY/SECRET/BASE/TOKEN/SUBS`，mtime **2026-06-30**）已约 3 个月未更新。

## 3. 为什么危害大于「少探一项」

- 错的口径产出的是**方向相反的结论**（「唯一好转项」），比「无数据」更糟——
  它会让人**停止怀疑该组件**，把注意力长期锁在错误的组件上（此处连续 3 天只看 5001）。
- 它同时污染了后续所有推理：既然云轨「好了」，那 read=0 只能是本地问题 →
  处置建议必然只指向「扫码重登」。
- 这类错误**不会自愈**：只要根路径还活着，探针永远「成功」，永远不会再暴露。

## 4. 通用教训

**探针必须打「真实业务端点」，不能用浅层可达性代替；能通过的最浅探针 = 最没用的探针。**

判定一个探针是否有效，问三个问题（与「readback 三问」同源）：
1. 它打的是**真实业务路径**吗？（根路径 `/`、`/health`、静态页 → 不算）
2. 它返回的**成功**能否与「业务真的产出数据」区分开？（HTTP 200 但 payload 为空 → 不算）
3. 它**失败时会怎样**？（若失败路径不可达/被吞 → 探针形同虚设）

**附带教训（上游真实生产者必须实证，不能靠命名推断）**：
本组自动化叫「本地微信通道」的组件（`localhost:5001`）长期被当作唯一上游，
但 `read_wx_articles.py` 的实际数据生产者是 `sync_wx_articles.py → wx_rss_auth → 云 RSS`，
5001 只是并行/降级轨。**「哪个组件是上游」要靠代码调用链证明，不能靠名字与部署直觉。**

**附带教训（修复不闭环）**：上游同步自动化 `automation-1785335108360`
【公众号】RSS文章同步落盘(每日) 自 2026-08-28 起 **PAUSED**。
即使通道修好，也没有 ACTIVE 链路把文章落到 `output/wx_articles/` → 下游仍会永远 `read=0`。
**修上游通道时必须连带确认「消费方自动化还活着」，否则修复不产生任何结果。**
