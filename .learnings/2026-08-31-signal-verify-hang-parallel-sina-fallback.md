# 2026-08-31 signal_verify 15:00挂死根治 — 串行网络×超时撞看门狗 + 多源兜底

**现象**：2026-08-31 15:00 信号溯源 STEP1 `python3 -m claw.monitoring.signal_verify` 被 15min 看门狗（SIGNAL_VERIFY_WATCHDOG=900s）强杀，恰 15m0s，报告未落盘。output 仅一行 `Wind 每日查询上限已达 (180次)`。当日上午 05:12 同脚本正常（435/460 verified）。

**根因**（证据链）：
1. **串行放大**：460 条信号仅 206 个唯一代码，但 `fetch_realtime` 按信号逐条调用（无按码去重）。收盘时段行情接口瞬时限流时单次 8s 超时 → 最坏 460×8s≈62min ≫ 15min 看门狗。
2. **二次补拉空耗**：tx qfq 端点(web.ifzq.gtimg.cn)当日返回 501 + Wind 日限 180 次/日用尽 + 裸 python3(3.13.12) 无 akshare → 全部 206 code 历史失败 → 二次补拉对每个 code `sleep(3)+sleep(1)` 重试 ≈ 14min，纯空耗。
3. **数据源随时段失效**：05:12 Wind 配额未用尽（历史来自 Wind）+ tx 正常 → 成功；15:00 Wind 耗尽 + tx 501 → 全挂。多源可用性随时段变化，单一静态优先级不够。

**修复**（commit b6627bf，3 处手术）：
- **实时价并行+去重**：`ThreadPoolExecutor(8)` 按 206 唯一代码并行预取 `_rt_cache`，主循环 `_rt_cache.get(code) or fetch_realtime(code)` 兜底。最坏 ~(206×8s/8)≈3.4min。
- **超时收紧**：gtimg 实时 8→6s、tx qfq 10→8s、akshare 15→8s。
- **系统性失败守卫**：二次补拉首轮失败率>70% 判定系统性故障（数据源全挂/日限/断网），跳过 206code×4s 重试。
- **新浪日线直连兜底** `_sina_daily_history`：quotes.sina.cn JSONP 轻量零依赖（实测 200/0.19s），插在 tx→Wind→**Sina**→akshare 之间。未复权原始价，由既有 -35% 嫌疑收益过滤兜底。

**验证**：修复后完整运行 **3m57s**（原 15min 强杀），报告 434/460 verified（94.3% 覆盖率，与 05:12 相当），win_rate 32.5%，avg_ret 3.52。权重/共识按新报告刷新（5 项变化）。

**✅已升级（通用铁律）**：
1. **串行 N 次网络调用 × timeout 是最隐蔽的挂死源**——先按业务键去重（460 信号→206 码），再并行化；单点串行 × 大 N × 超时 = 必然撞看门狗。
2. **重试前先判失败模式**：失败率 >70% = 系统性故障（重试纯空耗），<30% = 偶发限流（重试有效）；用失败率阈值区分，别一律重试。
3. **行情多源兜底按可达性动态生效**：一个端点 501/配额耗尽不代表全挂——用 curl 实测可达源（新浪 200）补位；兜底源可接受降级精度（未复权），用既有数据质量过滤护栏兜住。
