# 去重键不得用"完整告警文案"——改文案会静默重置去重窗口

**日期**：2026-08-31
**发现场合**：统一巡检中枢第 38 次运行（automation-1785982929477）
**等级**：🔴 高（静默失效，且自我掩盖——越优化文案越容易触发）
**状态**：已修复并验证（24 项断言全过，ruff 通过，生产实跑 4 键→3 键合并成功）

---

## 1. 现象

回读器报 `.ops_alerted.json` 有 **4 个去重键**，其中 **2 个指向同一个根因**（微信登录过期）：

| age | key |
|---|---|
| 53.95h | `微信公众号通道@wechat-download-api 登录过期(isExpired=true)，需扫码重登` |
| 23.22h | `微信公众号通道@wechat-download-api 登录过期(isExpired=true)，但通道早于过期即停摆，重登大概率无法恢` |

而该项 TTL 显式配置为 **72h**（`ALERT_DEDUP_TTL_OVERRIDE_H` 中唯一条目）。

## 2. 根因

去重键 = `f"{check_name}@{reason_key}"`，**`reason_key` 就是完整告警文案**。
调用点还有一记截断：`is_alert_duplicated(cname, rsn[:60])`。

于是：

- 08-29 推送时，文案是旧版（<60 字符，完整入库）
- 08-30 18:07，run#36 为提升准确性把文案改写为"但通道早于过期即停摆，重登大概率无法修复…"
  → 截 60 字符后成为**全新 key** → TTL 窗口被重置 → **同一根因 27 小时后又被推一次**

**结论：72h 降频设计被"改文案"架空。** 且这是**负反馈**——
历次巡检为提升可诊断性而改写文案（run#36 微信 F3 细化、run#37 告警明细改取 stdout），
**每改一次文案就多推一次、多留一个僵尸键**，键只增不减（2→4）。

## 3. 修复

```
_dedup_key(check_name, reason_key):
    取文案 → 在首个「，」或「（」处截断（只切中文标点，
              避免破坏 "登录过期(isExpired=true)" 这类 ASCII 括注）
          → rstrip(":： ")
          → 截断至 60 字符（与原调用点 rsn[:60] 效果一致，避免既有键一次性失效）
```

三点配套：

1. **截断权收归一**：删掉调用点 `rsn[:60]`，改由 `_dedup_key` 统一负责。
   原先"先截 60 再归一化"，若首个分隔符出现在 60 字符之后，**截断点抢先生效，归一化形同虚设**。
2. **历史键迁移**：`_load_alerted()` 读入时即归一化合并，**同组保留最新时间戳**。
   幂等——键已归一化后不再写盘（实测二次加载 mtime 不变）。
3. **只影响去重，不影响展示**：飞书卡片、审计日志仍用原始文案，诊断信息零损失。

### 安全性论证（关键）

合并时保留**最新**时间戳 → 合并后"距上次推送"只会更近 →
**合并只能增强抑制，不可能造成漏报**。这是本修复可以做进自动化的前提。

## 4. 验证（双向对照，24 项断言全过）

| 组 | 内容 | 结果 |
|---|---|---|
| A 故障条件复现 | 真实历史 4 键 → **3 键**，微信两条合一，保留最新 23.2h，TTL 仍 72h | ✅ |
| B 核心功效 | 连换三版措辞均命中同一键，键数不膨胀 | ✅×4 |
| C 正常路径 | 全新检查项/同项不同主体/长文案首次 → 均**可推送**（不得过度抑制） | ✅×5 |
| D run-id 区分性 | `:863` 处"run 标识前置"的设计意图**未被破坏**：不同 run 不同键、同 run 同键、尾部改词不影响 | ✅×3 |
| E 健壮性 | 空/None 文案、5 种损坏状态文件（`{}`/`[]`/`null`/非 json/值非数字）均不抛异常 | ✅×7 |
| F 幂等 | 二次加载内容一致、不重写盘 | ✅×2 |

**失败的一次是测试写错，不是代码错**：首轮我拿 `"剩余 5%"` 与 `"剩余 5%"+X*200`
两条**不同**消息断言"应去重" → 失败。正确断言是**同一条长消息重复两次**才去重。
→ 教训：**断言失败先检查断言本身**。

实跑后 `.ops_alerted.json` 4 键 → **3 键**，微信键保留 23.35h（下次推送 09-02 18:07，符合 72h），
`SUMMARY: checks=15 / alerts=1 / healed=0 / pushed=false`，SILENT 无推送。

## ★ 升级候选：通用规则

1. **去重/缓存/指纹的键，必须是"稳定身份"，不能是"呈现文本"。**
   任何会随诊断改进、措辞润色、i18n、日志格式调整而变化的字符串，都不配做键。
   展示层与身份层要分离。

2. **改监控判据/文案时，要检查它是否被别处当作标识符。**
   本次是"优化文案"这一个善意动作破坏了"降频"这个设计意图，二者分属不同关注点，
   改动者（run#36）无从察觉。

3. **发现"同一根因出现多个去重/状态键"时，优先怀疑键不稳定，而不是怀疑真的有多个问题。**
   判据：键的文本高度相似、时间跨度恰为 TTL 的零头。

4. **截断与归一化必须收敛到一处。** 分散在多处的截断会互相抢先生效，
   产生"看起来写了归一化、实际没生效"的静默失效（与 08-11「单链路日志≠全链路」同源）。

5. **合并状态键时保留最新时间戳**，可保证改动方向是"更强抑制"而非"漏报"——
   这让此类修复可以安全地放进无人值守自动化。
