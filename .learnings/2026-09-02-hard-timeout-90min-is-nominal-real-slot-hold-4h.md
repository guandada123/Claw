# 「90min 硬超时」是名义值 —— 实测占位 2~5.4 小时，被饿死的运行本身就是拥堵放大器

- 日期：2026-09-02（统一巡检中枢 run#70，23:55）
- 影响面：`unified_ops_center.py` 第 18 项检查（调度超发 / 硬超时）告警文案与因果模型
- 等级：★ 升级候选（修正了 run#67 起沿用三轮的一个载重结论）

## 现象

第 18 项检查的告警文案自 run#67 起写死「自动化硬超时 N 条被 [CANCELLED]（**90min 上限**）」。
run#68 报 8 条、run#69 报 7 条，读起来像「每条浪费 90 分钟」。

## 取证

把 `~/.workbuddy/logs/automation.log` 里的 `run start: id=X` 与
`run failed for X: [CANCELLED] Run timed out` 按 automation_id 配对，算 start→cancel 跨度：

| 指标 | 值 |
|---|---|
| 09-02 全天超时条数 | **26**（不是 7~8；哨兵只报锚点增量，单轮看不到全貌） |
| start→cancel 最短 | 121.5min |
| p50 | **238.3min** |
| 最长 | 323.7min（QTS日线全市场回填，16:30 起） |
| 落在 90min 附近的 | **0 / 26** |

且时长随当日拥堵**单调放大**：09:12 起 121min → 12:30 起 243min → 16:30 起 324min
→ 夜间负载回落后收敛到 168/174min。

## 结论

1. **90min 计的是「实际执行 / 无进展」时长，排队等待不计入。** 反例还有正向的：
   同一自动化 18:24 `run start` → 21:11 `run finished, success=true`（167min）也没被杀。
   所以 wall-clock 跨度既不能用来判超时，也不能用来判卡死。
2. **一条被饿死的运行不是"浪费 90min"，而是占着并发槽位 2~5 小时。** 这把
   run#67 的因果模型补完了：超发 → 争抢 → 单条变慢 → 占位时间被拉长 → 在飞数
   下不去 → 更严重的超发。**饿死者本身是正反馈的一环**，不只是受害者。
   这也解释了为什么"触发量全天稳定 90–106 条"却会拥堵坍塌 —— 不需要负载增长。

## 修复（本轮已落地）

- `_scheduler_log_signals()` 增加 start→cancel 配对，超时事件由 `(ts, id)` 扩为
  `(ts, id, held_min)`；负值（日志轮转配错 start）置 None，不编造。
- 新增 `_held_clause()`：告警/note 一律报**实测** p50/最长，名义 90min 仅作对照。
  无时长数据时返回空串（fail-safe，宁缺勿造）。
- 超发告警文案去掉"90min"字样。

## 可复用写法

1. **文案里的数字也是结论，会被当证据用。** 「90min 上限」是从平台报错文本推断的
   名义值，从没被实测验证过，却在三轮报告里当既成事实传播 —— 定期反查自己告警里
   的硬编码数字有没有实测支撑。
2. **哨兵的增量口径只适合"是否新增"，不适合"规模多大"。** 想知道当日总量必须另做
   全量统计；只看单轮告警数（7~8）会低估三倍以上。
3. **配对日志事件（start↔end）比读单侧事件信息量高一个量级** —— 单看
   `[CANCELLED]` 只知道"死了"，配上 start 才知道"死前占了多久槽位"，因果模型才闭合。
4. **同一现象的时长分布随时间单调漂移时，先怀疑计时口径而非阈值波动**（真固定阈值
   不会从 121min 漂到 324min）。
