# 「累计净差」被当成「当前并发」：一条每周必报 12 天的调度器超发告警

日期：2026-10-08（用户问「还有什么需要做的」→ 盘点 self-heal 发现时挖出）
级别：P2（不产生生产故障，但让「调度器超发」这个真实风险**永久失真**、且每轮推送）
状态：已修复并有回归测试（`tests/test_ops_center_dead_checks.py::test_scheduler_inflight_ignores_historical_unmatched_starts`）

## 现象

`unified_ops_center.py` 的 ④ 调度器超发检查，自 **2026-09-21** 起每一次运行都报：

> 调度器超发：当前在飞 **456** 条 ≥ 声明并发 3×2（日志峰值 462）——`concurrency=3` 未被强制执行，
> 运行相互饿死后会撞硬超时被 [CANCELLED]、产物全丢

而同一台机器上几十条自动化每天照常出产、当日 69 次运行全部 `result_success=1`。
**告警的文案很吓人，结论却是假的。**

## 真因：对整份日志 netting，未配对的 start 永久累加

`_scheduler_log_signals()` 原实现把整份 `~/.workbuddy/logs/automation.log`（11.8MB，08-29 起）
当事件流做扫描线：`run start` +1、`run finished` −1，走完的 `cur` 当作「此刻在飞」。

但 `run finished` **并不是每次都落**（被中断 / `[CANCELLED]` / 日志轮转），
未配对的 start 于是**只增不减**。实测把整份日志拆开数：

| 口径 | 结果 |
| --- | --- |
| 全文件 `start − finished` | 3250 − 2795 = **455**（= 告警里的「在飞 456」） |
| 近 2h / 6h / 12h / 24h / 36h / 72h 净差 | **0 / −1 / 0 / 0 / 0 / 0** |

即：**真实在飞 = 0**，告警数字是两个月历史残留的累加。

时间线也吻合：09-14~09-21 报「在飞 9~10、峰值 26」（尚可接受），
09-21 之后跳到 90 → 375 → 456 并长期停在 456、随日志增长每天 +1（458→462）。
**单调爬升 + 平台期 = 计数器在记"历史总量"，不是"瞬时量"。**

## 处置

- **在飞/峰值改为只在近 `SCHED_INFLIGHT_WINDOW_H`（= 硬超时回看 36h）内做扫描线**；
  实测修正后 `current=0 / peak=3`（峰值 3 与声明并发 3 吻合，可信）。
- **窗口外的未配对 start 不丢弃、单独计数上报**（`stale_unmatched=455`）——
  它是真事实（历史残留），只是**不是"在飞"**；不许静默吞掉，也不许冒充在飞。
- 告警/备注文案改为显式带「近 Nh」「同窗峰值」与残留计数，避免再出现"数字没有时间口径"。
- 回归测试：合成日志（5 条窗口外未配对 start + 窗口内 4 start/4 finished）
  断言 `current==0`、`peak==2`、`stale_unmatched==5`；并显式断言 `current != 5`
  （全文件净差）——已独立复核该测试在旧实现下必然失败。

## ★ 可复用教训

1. **★ 任何"当前 / 实时 / 在飞"指标，必须带时间窗口；对全量历史做累加得到的数不是瞬时量。**
   判据：如果它只增不减、或长期停在平台期而后缓慢爬升，它记的几乎一定是历史总量。
2. **★ 事件流 netting 的隐含前提是"配平"。** 只要有一类事件会丢（中断、取消、轮转、采样丢包），
   净差就会把"缺失的观测"当成"仍然存在"。配对类指标必须显式定义"未配对"怎么算，
   并把它单独计数出来，不能混进主指标。
3. **★ 警报数字必须自带口径**（时间窗、分母、采样面）。"在飞 456 条"与"近 36h 在飞 0 条"
   在文案上只差几个字，但一个让人去救火，另一个让人继续干活。
4. **★ 长期每轮必报的告警 = 死守卫的另一种形态。** 本例告警天天报、数字还在变（456→457），
   看起来"活着"，实际判据早已失真 —— 与「恒绿假通过」同族，只是方向相反。
   排查入口：**先问"这个数从哪来、时间口径是什么"，再问"是不是真的"**。
