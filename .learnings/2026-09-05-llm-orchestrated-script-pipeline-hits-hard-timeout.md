# LLM 逐步编排纯脚本任务 = 把执行时间暴露给队列，拥堵时撞硬超时

**日期**：2026-09-05
**等级**：P0（三个数据产物停更 73 小时，选股/策略消费陈旧数据）
**状态**：已修复并验证
**✅已升级(2026-09-06)**：是（适用于所有「agent 一步步跑脚本」的自动化）

---

## 1. 现象

「📊【知识库】信号溯源+升降级+CSV(05:00)」连续 4 天失败：

| 运行 | 耗时 | 结果 |
|---|---|---|
| 09-01 05:05 | **8.6 分** | ✅ 成功 |
| 09-02 05:05 | 36.6 分 | ❌ interrupted |
| 09-03 05:05 | **90.0 分** | ❌ Run timed out |
| 09-04 05:05 | **90.0 分** | ❌ Run timed out |
| 09-05 05:05 | 82.8 分 | ❌ terminated |

后果：`qts_regime.json` / `signal_consensus.json` / `source_weights.json`
从 09-02 05:06~05:53 起停更 **73 小时**，期间选股、策略、信号权重全在用三天前的数据。

## 2. 取证：先逐个排除错误归因

| 假设 | 验证方式 | 结论 |
|---|---|---|
| 脚本坏了？ | 逐个直跑 | ❌ 排除：脚本全跑通，合计仅 **5.7 分钟** |
| 调度锁残留？ | 看 `check_schedule` 实现 | ❌ 排除：锁文件按日期命名，且 `done_schedule` 才建锁，中断不会留下锁 |
| 非交易日跳过？ | 跑 `is_trading_day.py` | ❌ 排除：09-02~09-04 是周三至周五，交易日 |
| 任务自身变慢？ | 对比 09-01 成功耗时 | ❌ 排除：脚本 5.7 分从未变过 |

**关键数据**：09-01 成功那次总耗时 8.6 分钟，而脚本实际只需 5.7 分钟
→ **LLM 逐步编排的开销约 3 分钟**。

## 3. 根因：编排开销随队列膨胀 30 倍

调度器超发未限流（`concurrency=3` 未生效，在飞峰值 21→26），
LLM agent 执行的**每一步**（推理 + 工具调用）都要排 LLM 队列。
7 条命令 × 拥堵系数 → 编排开销从 **3 分钟膨胀到 80+ 分钟**，
总时长撞上 90 分钟硬超时，整轮被杀、产物全丢。

耗时分布（实测，能看出主次）：

```
sync_combo_signals.py        0.3s
pull_qts_signals.py          0.4s
export_qts_regime.py         0.6s
signal_verify            304.9s  ← 98% 的时间集中在这一个脚本
compute_signal_weights.py    0.4s
source_weight.py             0.3s
signal_consensus.py          0.3s
──────────────────────────────────
脚本合计                 307.1s（5.1 分钟）
```

**放大效应**：脚本占比越小，LLM 编排的"税"越显得冤。
这里脚本只占 5.7/8.6 = 66%，但拥堵时编排侧涨到 80+ 分钟，成了**主要成本**。

## 4. 修复

新建 `Claw/scripts/signal_trace_pipeline.py`，把 7 条命令串行编排进单个脚本：
- 单步失败**不中断**全流程（原 agent 模式正是某步卡住拖垮整轮）
- 每步计时打印，耗时分布可见
- 内置 `PYTHONPATH=$CLAW/src`（STEP1 依赖 claw 包，08-31 曾因此 ModuleNotFoundError）
- 结束后**回读产物 mtime 做新鲜度自检**（"跑了"≠"写出了"）
- 退出码区分：关键步骤失败=1，仅非关键失败=0（避免噪音告警）

两个自动化（05:00 / 15:00）的 prompt 同步改为 v10.0：
保留交易日门禁、anysearch 退避、L3 护栏、调度锁、推送判断，
只把「LLM 逐步执行 7 条命令」换成「单次脚本调用」。

## 6. 通用教训

**① 「任务跑多久」-「脚本跑多久」= LLM 编排开销。**
这个差值正常时是常数（几分钟），拥堵时会**非线性膨胀**（此处 30 倍）。
判断一个自动化会不会撞硬超时，看的是**膨胀后的值**，不是脚本耗时。

**② 纯脚本编排的任务，不该让 LLM 一步步执行。**
LLM 的价值在判断（要不要推、推什么），不在搬运命令。
把执行交给脚本，agent 只做决策 —— 既稳又省钱（省 reasoner 编排 token）。

**③ 排查"任务失败"时，先分离"执行体"与"编排体"。**
直跑一遍脚本就能把故障域砍掉一半。本次若直上一顿调超时参数，
永远修不好 —— 因为超时的不是脚本，是排队。

**④ 产物新鲜度检查要回读文件 mtime，不能只看"任务跑没跑"。**
本次三个产物停更 73 小时，而任务每天都"跑了"（只是每次都死在半途）。
跑了 ≠ 写出了。

**⑤ 顺带确认的无关项**：QTS 日线回填同样连续 3 次 success=0，
但查库发现 `daily_quote` 最新交易日 4892 行、近 8 日全部达标 —— 数据已落库，
只是结论被判失败。**同类告警要先验数据，别按同一套处置。**

## 7. 审计补充（2026-09-05 脚本化变更复审）

**⑥ 覆盖式注入子进程 env 会丢 preamble 追加路径。**
preamble 设 PYTHONPATH 是前置追加（`"$CLAW/src:$PYTHONPATH"`），
wrapper 首版用 `{"PYTHONPATH": src}` **整体覆盖** → vendor/shim 等 preamble
追加的路径全被丢弃（P1，已修）。凡是 subprocess 且需补充 PYTHONPATH，
一律**去重 + 前置**（src 置首位、其余原样保留），与 preamble 的追加语义一致。
改子进程 env 前先读 preamble 的赋值方式（追加 or 覆盖），别想当然。

**⑦ 双路径"疑似双副本"先查挂载关系再下结论。**
`/Users/guan/WorkBuddy` 与 `/Volumes/ZHITAI/WorkBuddy` 同时可读 → 疑漂移风险。
定案工具链：`stat -f '%d %i'`（dev+inode）+ `md5` 比对 + `readlink` 查父级。
结果：`/Users/guan/WorkBuddy` 是软链 → ZHITAI 卷，dev=16777240 / inode=3152741
**完全相同 = 同一文件**，非副本。此类核查用 inode/dev 一锤定音，勿凭直觉判双写。
